# 示例跨系统需求分析

> 读者：**需求分析师**与**产品/架构**。
> 本文件为 `company/analysis/` 下的示例分析，用于展示跨系统需求分析在 company 层的推荐写法。

---

## 1. 背景与目标

### 1.1 需求背景

- 关联解决方案：`solutions/SOLUTION-EXAMPLE.md`
- 场景说明：业务侧需要在公司层先完成“跨系统目标、边界、依赖、风险”的收敛，再由各系统拆分承接。

### 1.2 需求目标

| 目标编号 | 目标描述 |
| -------- | -------- |
| G-1 | 明确跨系统目标、边界与承接关系 |
| G-2 | 为后续系统侧需求拆解提供统一起点 |
| G-3 | 让参与方在 company 层先对范围、影响与风险形成共识 |

### 1.3 范围与边界

#### 范围内（In Scope）

- 说明跨系统目标、关键参与方与分析边界。
- 记录需要由各系统后续承接的需求主题与依赖关系。
- 为下游 PRD/ASD/DSD/TDD 提供统一起点。

#### 范围外（Out of Scope）

- 不在 company 层展开系统实现设计、接口细节或数据模型。
- 不替代各系统侧的正式 requirements 包。

#### 假设与约束

- 假设业务目标已在 `SOLUTION-EXAMPLE` 中达成初步共识。
- 假设系统边界与公司级实体命名已具备统一口径。

### 1.4 业务价值

- 在公司层先统一跨系统口径，减少后续多系统各写一版分析导致的漂移。
- 让系统侧承接物聚焦本系统职责，不重复重写跨系统背景。

---

## 2. 范围与约束

### 2.1 核心场景

业务方提出一项跨系统改进诉求，需要先在公司层确认哪些系统参与、哪些规则需要统一、哪些内容留到系统侧细化。

### 2.2 关键参与方

| 角色 | 关注点 | 说明 |
| ---- | ---- | ---- |
| 业务负责人 | 目标、范围、优先级 | 确认为什么做、做到哪 |
| 产品/分析 | 业务规则、验收口径 | 负责把目标拆成可承接需求 |
| 系统负责人 | 系统边界、依赖、风险 | 确认由谁承接、如何分段 |

### 2.3 范围约束

- 公司层只保留跨系统分析，不承载落地设计细节。
- 产出必须可被一个或多个 `system/requirements/REQUIREMENT-{IDEA-ID}/` 承接。
- 若存在未知项，应显式记录在待澄清问题中，而不是省略。

### 2.4 交付约束

- 先形成最小可评审分析，再由各系统按职责推进。
- 若仅为模板演示，可保留“示例”内容，但结构必须与现行模板一致。

## 3. 影响与冲突

### 3.1 影响面

- 影响 `company/solutions/` 与 `company/analysis/` 的同链追溯关系。
- 影响各系统需求承接入口与责任边界划分。

### 3.2 影响业务能力

| 能力 | 影响程度 | 影响说明 |
| ---- | ---- | ---- |
| 跨系统需求收敛 | 高 | 先在公司层完成共识，再进入系统侧承接 |
| 责任边界澄清 | 高 | 提前明确哪些内容留在 company 层、哪些交由系统侧承接 |
| 追溯一致性 | 中 | 保持方案、分析与后续承接文档的关系可追溯 |

### 3.3 影响传播路径

`company/solutions/` -> `company/analysis/` -> `system/requirements/`

### 3.4 业务冲突

| 冲突编号 | 冲突描述 | 严重程度 | 化解方案 |
| -------- | -------- | -------- | -------- |
| C-1 | 公司层分析与系统侧承接边界不清 | 中 | 在 analysis 中明确“到此为止”的边界，并在系统侧再细化 |

---

## 4. 思路与方案

### 4.1 解决思路

以“跨系统目标先收敛、系统侧再承接”为主线，在 company 层先明确范围、参与方、影响、风险与分阶段计划，再由各系统按职责细化。

### 4.2 方案对比

| 方案 | 描述 | 优点 | 风险 |
| ---- | ---- | ---- | ---- |
| A | 先在 company 层完成跨系统分析，再分发到系统侧承接 | 边界清晰、便于统一口径 | 需要多方先达成共识 |
| B | 各系统直接分别分析，再事后汇总 | 启动快 | 口径容易漂移、追溯成本高 |

### 4.3 关键决策

| 决策点 | 推荐方案 | 选定理由 |
| ------ | -------- | -------- |
| 跨系统分析放在哪一层先收敛 | A | 先在 company 层统一范围和边界，再进入系统侧承接更稳定 |

## 6. 交付计划

### 6.1 MVP 拆分

| MVP阶段 | 核心内容 | 业务价值 | 依赖关系 |

| MVP-1 | 明确跨系统目标、参与方与承接边界 | 各方先形成统一认知 | 无 |
| MVP-2 | 补齐风险、依赖与分阶段计划 | 便于系统侧继续细化与排期 | MVP-1 |

### 6.2 关键里程碑

| 里程碑 | 交付物 | 验收标准 |
| ------ | ------ | -------- |
| 里程碑-1 | company 层分析初稿 | 目标、边界、参与方已达成基本共识 |
| 里程碑-2 | 系统侧承接计划 | 各系统已明确自身承接内容与依赖 |
