# 示例跨系统需求分析

> **结论**：选方案 A——公司层先收敛跨系统目标/边界/风险，再由各系统承接。  
> 读者：需求分析师、产品/架构。路径：`company/analysis/`。上游：`solutions/SOLUTION-EXAMPLE.md`。

---

## 1. 背景与目标

### 1.1 需求背景

关联 `SOLUTION-EXAMPLE`：业务侧须在公司层先收敛跨系统目标、边界、依赖、风险，再由各系统拆分承接。

### 1.2 需求目标

| 目标编号 | 目标描述 |
| -------- | -------- |
| G-1 | 明确跨系统目标、边界与承接关系 |
| G-2 | 为后续系统侧需求拆解提供统一起点 |
| G-3 | 参与方在 company 层先对范围、影响与风险形成共识 |

### 1.3 范围与边界

#### 范围内（In Scope）

- 跨系统目标、关键参与方与分析边界
- 各系统后续承接的需求主题与依赖
- 下游 PRD/ASD/DSD/TDD 的统一起点

#### 范围外（Out of Scope）

- 不展开系统实现、接口或数据模型
- 不替代各系统正式 requirements 包

#### 假设与约束

- 业务目标已在 `SOLUTION-EXAMPLE` 初步共识
- 系统边界与公司级实体命名已有统一口径

### 1.4 业务价值

公司层先统一跨系统口径，减多系统各写一版导致的漂移；系统侧承接物聚焦本职，不重写跨系统背景。

---

## 2. 范围与约束

### 2.1 核心场景

跨系统改进诉求 → 公司层确认参与系统、须统一规则、可留系统侧细化项。

### 2.2 关键参与方

| 角色 | 关注点 | 说明 |
| ---- | ---- | ---- |
| 业务负责人 | 目标、范围、优先级 | 确认为什么做、做到哪 |
| 产品/分析 | 业务规则、验收口径 | 目标拆成可承接需求 |
| 系统负责人 | 系统边界、依赖、风险 | 谁承接、如何分段 |

### 2.3 范围约束

- 公司层只保留跨系统分析，不承载落地设计细节
- 产出须可被一个或多个 `system/requirements/REQUIREMENT-{IDEA-ID}/` 承接
- 未知项显式记入待澄清，不省略

### 2.4 交付约束

- 先最小可评审分析，再按系统职责推进
- 模板演示可保留「示例」内容，结构须与现行模板一致

## 3. 影响与冲突

### 3.1 影响面

- `company/solutions/` ↔ `company/analysis/` 同链追溯
- 各系统需求承接入口与责任边界

### 3.2 影响业务能力

| 能力 | 影响程度 | 影响说明 |
| ---- | ---- | ---- |
| 跨系统需求收敛 | 高 | 公司层先共识，再入系统侧 |
| 责任边界澄清 | 高 | 明确 company 层止点与系统侧承接 |
| 追溯一致性 | 中 | 方案、分析与承接文档可追溯 |

### 3.3 影响传播路径

`company/solutions/` → `company/analysis/` → `system/requirements/`

### 3.4 业务冲突

| 冲突编号 | 冲突描述 | 严重程度 | 化解方案 |
| -------- | -------- | -------- | -------- |
| C-1 | 公司层分析与系统侧承接边界不清 | 中 | analysis 写清「到此为止」；系统侧再细化 |

## 4. 思路与方案

### 4.1 解决思路

**结论**：跨系统目标先收敛，系统侧再承接——company 层先定范围、参与方、影响、风险与分阶段计划。

### 4.2 方案对比

| 方案 | 描述 | 优点 | 风险 |
| ---- | ---- | ---- | ---- |
| A | company 层先跨系统分析，再分发系统侧 | 边界清、口径易统一 | 须多方先共识 |
| B | 各系统分别分析，事后汇总 | 启动快 | 口径易漂、追溯成本高 |

### 4.3 关键决策

| 决策点 | 推荐方案 | 选定理由 |
| ------ | -------- | -------- |
| 跨系统分析放在哪一层先收敛 | A | 先统一范围与边界，再入系统侧更稳 |
