# 示例跨系统解决方案

> **结论**：选方案 A——以业务对象为中心做统一视图，并收敛可追溯口径（G-1 / G-2）。  
> 读者：业务与产品。示例路径：`company/solutions/`。

---

## 1. 背景与目标

### 1.1 业务现状

多系统共担同一业务链路；业务侧缺单一视角下的统一状态与可追溯信息。

### 1.2 存在问题

信息分散、多入口切换 → 排查慢、协作成本高、对外口径易不一致。

### 1.3 业务目标

- G-1 跨系统关键状态聚合为统一视图，快速定位「卡在哪」。
- G-2 对外承诺口径落到可验证业务规则，减解释成本与争议。

### 1.4 业务价值

少对账往返；快响应；稳客户体验（口径一致）。

---

## 2. 范围与约束

### 2.1 核心场景

单入口查询业务对象 → 返回各系统关键状态、时间点、下一步建议。

### 2.2 涉及角色

| 用户角色 | 角色描述 | 核心关注点 |
| -------- | -------- | ---------- |
| 业务人员 | 流转与对外解释 | 状态可见、口径一致 |
| 运营人员 | 时效与异常 | 时效、异常定位 |
| 协作方 | 链路环节处理 | 交接清晰、可追溯 |

### 2.3 范围边界

#### 范围内（In Scope）

- 单一业务对象：跨系统关键状态统一展示与追溯
- 与业务规则一致的状态解释与下一步指引

#### 范围外（Out of Scope）

- 不改既有业务规则（仅统一口径与呈现）
- 不改各系统原处理流程（仅补展示/追溯字段口径）

#### 成功标准

- 单入口完成状态查询与定位，解释口径一致
- 典型问题定位耗时显著下降（业务可验收口径）

### 2.4 关键约束

#### 业务约束

- 对外口径必须一致；冲突时以业务规则优先级 + 可追溯证据为准

#### 资源约束

- 最小改动；优先高频链路与高价值对象

#### 技术约束

- 正文只用业务可读方式写能力限制；不展开工程实现

#### 交付约束

- 无外部硬截止则按业务优先级分阶段；每阶段可独立验收

---

## 3. 影响与冲突

### 3.1 影响面

- 业务：统一视图，少多处查询
- 运营：异常定位路径更短、追溯更集中
- 协作方：关键状态口径须一致且可追溯

### 3.2 影响业务能力

| 功能/业务能力 | 影响程度 | 影响类型 | 影响说明 |
| ------------ | -------- | -------- | -------- |
| 状态查询 | 高 | 口径调整 | 多入口 → 统一视图 |
| 异常定位 | 中 | 追溯增强 | 关键时间点与责任归属提示 |
| 对外解释 | 高 | 承诺一致性 | 统一规则 + 证据支撑口径 |

### 3.3 影响传播路径

```text
[状态查询] → [异常定位] → [对外解释] → [跨团队协作]
```

### 3.4 业务冲突

| 冲突编号 | 冲突描述 | 冲突类型 | 严重程度 | 化解方案 | 化解成本 |
| -------- | -------- | -------- | -------- | -------- | -------- |
| C-1 | 不同系统对同一状态命名/判定口径不一致 | 规则/流程/数据冲突 | 中 | 统一口径并补齐可追溯证据 | 中 |

---

## 4. 思路与方案

### 4.1 解决思路

**结论**：业务对象中心统一视图 = 对齐状态口径 + 补齐追溯 + 说明现状与下一步（业务可读）。

### 4.2 方案对比

| 对比维度 | 方案A | 方案B |
| -------- | ----- | ----- |
| 业务匹配度 | 高：统一视图 + 统一口径 | 中：仍靠人工对齐 |
| 实现复杂度 | 中：口径与追溯对齐 | 低：仅文档约定 |
| 影响范围 | 中：多系统协同 | 低 |
| 风险程度 | 中：口径需共识 | 中：口径仍易漂移 |
| 可扩展性 | 高：可扩覆盖 | 低：靠人工 |

### 4.3 关键决策

| 决策点 | 推荐方案 | 备选方案 | 选定理由 |
| ------ | -------- | -------- | -------- |
| 统一视图是否引入口径收敛 | 方案A | 方案B | 无口径收敛则争议持续；统一视图须以可追溯口径为基础 |
