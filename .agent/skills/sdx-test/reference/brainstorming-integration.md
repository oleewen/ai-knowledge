# brainstorming 与 sdx-test 的衔接（嵌入层）

本文件说明：在 **`/sdx-test` 阶段二**如何把 **brainstorming** 的对话节奏嵌入门禁 **G{n}**，并与 Q-n、C/M/S/F 协同。执行阶段二时**建议打开本文**，避免与独立执行 `/brainstorming` 时的默认产物与终态混淆。

---

## 与独立 `/brainstorming` 的差异（须牢记）

| 维度 | 独立 `/brainstorming` | 本技能内嵌（阶段二） |
|------|----------------------|----------------------|
| 主产物 | 常为 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` | 会话 spec：`...-sdx-test.md`；终稿：`TDD-*.md` |
| 正常终态 | 经批准后进入 `writing-plans` 等实现计划 | **Qclose-1** → 阶段三分块定稿；**不**在本会话内以 `writing-plans` 作为默认收尾 |
| HARD-GATE | 以 brainstorming 技能为准 | **仍以 sdx-test HARD-GATE 为准**：总确认前默认不写 `{DOC_DIR}/requirements/**/TDD-*.md` |

**禁止**：在仅执行 `/sdx-test` 的对话中，用「已完成 brainstorming」为由跳过 Gn 收口、门禁标记或 Qclose-1；也**禁止**默认创建 `*-design.md` 替代本会话 spec。

若用户**明确需要**一份独立设计 spec，应**另开会话**执行 `/brainstorming`，再在后续会话用本技能消费其结论。

---

## 嵌入层：何时触发

在阶段二**任意门禁 G{n}** 内，出现以下任一情况，即进入 **brainstorming 式子流程**：

1. **多套可取舍方案**：同一门禁下存在两条及以上**真实可选**的路径（测试层次取舍、回归范围、数据准备策略、进出标准阈值等），需要用户做取舍。
2. **需要结构化权衡**：信息足够但**利弊并存**，需对比后再写入「本门禁结论」。

**不必触发**：仅有一个合理路径、或仅需澄清事实而无方案分叉时，按原有草案 → 确认点 → 收口即可。

---

## G{n} 内「多方案」子流程（推荐顺序）

在**该 G{n} 未收口前**完成：

1. **点名方案**：列出 **2–3 套**，名称须为**业务语义**，避免空洞的「方案A/方案B」字样。
2. **利弊与取舍**：每套给出适用条件、成本/风险要点、不适用场景；给出**推荐项及理由**（可被拒绝）。
3. **用户确认**：用标准四选项（C/M/S/F）收口本门禁；结论写入 spec「本门禁结论」，并注明被选方案及未选方案的搁置理由（若适用）。

**与 Q-n 的分工**：Q-n 解决**信息缺口**；本节解决**信息足够但决策分叉**。若分叉内仍有事实缺口，先收敛 Q-n，再回到方案对比。

---

## 与各门禁的典型触发（非穷尽）

| 门禁 | 可能出现的「多套方案」示例 |
|------|--------------------------|
| G1 | 测试层次配比、覆盖率目标与项目现实的权衡 |
| G2 | 用例粒度、P0 边界、是否单独列出某类异常 |
| G3 | 数据脱敏 vs 合成数据、脚本化程度 |
| G4 | Mock 深度、环境对齐生产 vs 简化环境 |
| G5 | 退出标准严格度、缺陷容忍策略 |
| G6 | 附录粒度、对外承诺级别 |

**G2** 常为多方案密集区，但**不限于此**：只要当前 G{n} 的结论依赖方案选择，就应在本门禁内完成对比再收口。
