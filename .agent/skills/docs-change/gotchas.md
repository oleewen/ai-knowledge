# docs-change 常见陷阱

补充 SKILL.md 约束的场景说明——遇到具体问题时来这里查。

---

## 时间基准相关

**baseline vs cutoff 混淆**
这是最高频的错误。`baseline_time` 和 `cutoff_time` 是两个不同的值：
- Git 来源用 `baseline_time` 过滤（从上次索引结束时间起）
- CHANGELOG 和本地文件用 `cutoff_time`（= `max(baseline, latest_git_commit)`）过滤

用错会导致冗余条目或漏收。两个值相同只是巧合，不要假设它们总是一样。

**增量时忘读已有基线**
增量执行时必须先读 `CHANGE-LOG.md` 文末 `<!-- docs-change:baseline_time_ms=... -->`，否则会用默认值 `2020-01-01` 重复收录全量历史，产出一份几乎没有增量价值的日志。

**时间格式不统一**
不同来源的时间格式各异（ISO 8601、自定义字符串等），比较时一律转为 13 位毫秒戳再做大小判断，不要用字符串比较。

---

## 数据采集相关

**输出目录自引用**
扫描本地文件 mtime 时，必须将 `{output_dir}` 加入排除列表。否则每次执行都会把上次写入的 `CHANGE-LOG.md`、`INDEXING-LOG.md` 等收录为变更，形成循环——每次运行都会产生新条目，基线永远无法稳定。

**Git 不可用时终止**
Git 检测失败应优雅降级（输出 `[WARN]`，跳过 git 来源），不应终止整个流程。CHANGELOG 和本地文件来源仍需继续采集——用户可能在没有 git 的环境下运行。

**CHANGELOG 解析失败静默丢弃整个文件**
某条目日期格式不匹配时，只跳过该条目并输出 `[WARN]`，继续解析同文件其余条目。丢弃整个文件会导致大量有效变更记录丢失。

---

## 输出处理相关

**增量执行覆盖历史**
增量模式必须将新变更**追加**到已有 `CHANGE-LOG.md`，不能清空历史记录。历史条目一旦丢失，`baseline_time` 也随之丢失，下次增量会退化为全量，审计链断裂。

**合并后未排序**
三源数据合并后必须统一按时间倒序排列再写入，否则日志可读性差，下游工具解析时也可能出错。

**来源标注缺失**
每条变更记录必须标注来源（`git` / `changelog` / `local`），下游 `docs-build` 依赖此信息分流处理。缺少来源标注会让下游无法区分提交历史和文件变更。

---

## 与下游协作相关

**输出路径与下游约定不一致**
未指定 `--output` 时默认输出到 `./changelogs/`，下游 `docs-indexing` 也从此路径读取。若输出到 `./{DOC_DIR}/changelogs/` 而下游期望 `./changelogs/`，增量模式会降级为全量。确认输出路径时要同时考虑下游的读取位置。

## 快速自查清单

- [ ] 时间基准按优先级正确读取（`--since` > 已有基线注释 > 默认值）
- [ ] `cutoff_time = max(baseline_time, latest_git_commit_time)` 计算正确
- [ ] 所有时间比较使用毫秒戳，不用字符串比较
- [ ] 输出目录已从本地文件扫描中排除
- [ ] Git/CHANGELOG 不可用时已优雅降级，未终止流程
- [ ] 增量执行未清空历史记录
- [ ] 条目按时间倒序排列
- [ ] 每条变更记录含来源标注（git / changelog / local）
- [ ] 文末基线注释已更新为本轮最新 `baseline_time_ms`
