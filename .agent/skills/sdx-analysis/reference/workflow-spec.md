# 工作流规范（sdx-analysis）

SKILL.md 中的流程为主干，本文件补充门禁状态机、精简/全量映射、回跳影响面、Q-n 协议与各 G{n} 填充要点。

---

## 门禁状态机

```
[阶段一：参数确认]
    ↓ 全部参数确认（或 S/F 跳过）
[阶段二：逐门禁交互]
    全量 6G：G1 → G2 → G3 → G4 → G5 → G6
    精简 4G：G(1–2) → G3 → G4 → G(5–6)
    每门禁：草案呈现 → （可选）多方案对比 → 待确认点逐一确认 → 门禁收口
    多方案对比：见「G{n} 内多方案子循环」与 [brainstorming-integration.md](brainstorming-integration.md)
    ↓ 全部门禁收口（或 S/F 跳过）
[Qclose-1 总确认]
    ↓ C / S（PENDING → CONFIRMED）
[阶段三：文档生成]
    骨架 → chunk 1 → … → chunk 6 → 终检
```

## 回跳影响面评估

用户回跳到 G{k} 并修改结论后，评估后续门禁的依赖类型：

| 依赖类型 | 判断标准 | 处理方式 |
|---------|---------|---------|
| 强依赖 | 后续门禁与 G{k} 新结论显式矛盾，或引用同一实体（同一 FR/MVP/R、同一范围边界） | 须重新确认 |
| 弱依赖 | 后续门禁大量引用 G{k} 的术语、范围、优先级或验收表述 | 建议重新确认 |
| 无依赖 | 后续门禁内容与 G{k} 无关联 | 保持已确认状态 |

**典型示例**：回跳 G2 增删 FR-n 或改优先级 → G4 MVP 包含关系、G5 依赖与风险往往为**强依赖**；回跳 G1 改 In/Out → G2–G5 多需重审至少弱依赖。

向用户说明影响面后，由用户选择「仅强依赖重走」或「强弱一并重走」。

## G{n} 内多方案子循环

**触发**：当前门禁的结论依赖**两条及以上真实可选路径**（FR 切分、MVP 切法、非功能取舍、风险应对等），需要先取舍再定稿。详见 [brainstorming-integration.md](brainstorming-integration.md)。

**节奏**（仍在同一 G{n} 内，未收口前）：

1. 列出 2–3 套路径，**业务语义命名**（避免空洞的「方案A/B」）。
2. 利弊、适用条件、推荐及理由。
3. 用标准四选项收口，结论写入 spec「本门禁结论」。

**与 Q-n 的分工**：Q-n 解决**信息缺口**；本节解决**信息足够但决策分叉**。若分叉内仍有事实未清，先 Q-n，再回到方案对比。

## 待澄清项（Q-n）交互协议

**触发时机**：阶段二任意门禁中出现歧义、矛盾或信息缺失时，立即标注 Q-n。

**交互格式**：

```
Q-{n}：{问题描述}

背景：{为什么需要澄清，影响哪个决策}

选项：
1. {具体业务含义描述}（推荐）
2. {具体业务含义描述}
3. {具体业务含义描述}
4. 其他（请说明）

请选择：
C：确认选项 1（推荐）
M：修改，格式 "M 旧内容 - 新内容"
S：跳过，标注为待澄清
F：跳过门禁，拟定草稿
```

**规则**：
- 每次只提一个 Q-n，等用户回答后再提下一题
- 选项描述具体业务含义，不写「方案A/方案B」等抽象标签
- 澄清结论写入 **§1.3**、范围与边界或对应 **FR-n**，不单独设「待澄清问题」章
- 用户选 S 时，在 spec 中标注「Q-{n} 待澄清」并说明影响范围

**Q-n 优先模式**（可选）：当同一份 spec 中登记了多条 Q-n 且用户希望先收敛歧义时，可在全部门禁草案完成后，先逐一确认所有 Q-n，再进行分门禁摘要确认，最后进入 Qclose-1。

## G{n} 填充要点

### G1：§1 背景目标（深度研究）

1. **通读解决方案**：提取业务目标（§1.2 用 **G-n** 与上游对齐）、核心场景、影响面、已知风险。
2. **四维度研究**（内部分析可对照技术索引；**写入 §1.3 时仅用业务/协作语言**）：

   | 维度 | 研究内容 |
   |------|---------|
   | 领域边界 | 上下游责任划分、核心概念与业务对象 |
   | 核心规则 | 现有业务规则、流程阶段、约束 |
   | 跨域协作 | 信息如何在团队/系统间传递 |
   | 行业与对内惯例 | 同类场景的常见做法与陷阱 |

3. **落位 §1.3**：范围与边界（In/Out，与解决方案差异须说明）；假设与约束；研究与分析（调研结论、核心规则发现、跨域协作要点）。
4. **知识库盲区**：解决方案中提到的概念在知识库中找不到对应实体时，在 §1.3 中显式标记「研究盲区」。

**depth 影响**：`quick` 仅研究领域边界与核心规则；`standard` 完整四维度；`deep` 增加对标与可行性要点。

### G2：§2 功能需求

1. 为每个 **FR-n** 独立成节（`### FR-nnn: {名称}`），每节包含：描述、输入、处理逻辑（含 **BR-n** 规则表）、涉及的业务对象表、输出、异常与边界、验收标准。
2. **§2 顶部概览表**：FR 编号、名称、优先级（P0–P3）、所属 MVP、关联 G-n。
3. **BR-n** 落在对应 FR-n 节内；被多个 FR 引用时，首条 FR 详述，其余交叉引用。
4. **不单独设「数据需求」章**，业务对象用各 FR 内「涉及的业务对象」表承载。

**depth 影响**：`quick` 仅细化 P0/P1；`standard` 完整细化；`deep` 增加需求间依赖与历史数据影响的业务说明（物理表结构等不写正文，可列入 §6.3 标注「待研发确认」）。

### G3：§3 非功能需求

按模板 **§3.1–§3.5**：体验与性能、可用性与连续性、安全与合规、可追溯与问题定位、兼容与升级。优先**用户与业务可感知**表述；量化工程指标可写「须与研发共拟」。

### G4：§4 交付计划（MVP 拆分）

1. **拆分原则**：独立业务价值、单向依赖、P0 优先、共性能力随首个依赖它的 MVP 交付。
2. **§4.1** MVP 总览表（阶段、目标、包含需求、交付价值、工期、前置依赖）。
3. **§4.2** 各 MVP 目标、范围、验收、依赖项（按模板分节）。
4. **§4.3** MVP 依赖关系图（文本/ASCII），确保无环。

### G5：§5 依赖与风险

1. **§5.1 依赖关系**：覆盖功能/数据/对接与协作/外部四类；正文写「谁须在何时交付什么结果」，主表避免技术接口名。
2. **§5.2 风险评估**：R-n，标注可能性（高/中/低）与影响（高/中/低）；高风险须有产品与协作侧可执行的应对与跟进。

### G6：§6 附录与定稿整合

1. **§6.1** 术语、**§6.2** 参考、**§6.3** 变更历史（技术线索归宿，标注「待研发确认」）、**§6.4** 质量自查表。
2. **语言审读**：通读全文，去除不当技术术语；确需保留的工程线索集中至 §6.3。
3. **文末文档元数据**（fenced `yaml`；勿在文件开头写 `---`）：`id`、`title`、`version`、`status`、`created`、`updated`、`author`、`reviewers`、`parent`（填 `SOLUTION-{IDEA-ID}`）、`tags`。
4. **质量门禁**：对照 [quality-checklist.md](quality-checklist.md) 与模板 §6.4 逐项判定；仅当通过标准已满足，方将 `- [ ]` 改为 `- [x]`。
