# 核心原则与规范（sdx-solution）

本文件定义 sdx-solution 技能的核心概念、设计原则、编号规范及反模式，作为方案定义阶段（步骤 1–5）的最高执行准则。

---

## 1. 核心概念

### 1.1 IDEA-ID
**IDEA-ID** 为需求链的唯一标识，对应文件命名格式 `*-{YYMMDD}-{主题}` 中的 `{YYMMDD}-{主题}` 段：
- **`{YYMMDD}`**：六位日期（年两位 + 月两位 + 日两位）。
- **`{主题}`**：简明短名，**优先使用中文**（2～20 字），可读可检索。
- **ASCII 备选**：仅当环境强制要求时使用英文 `kebab-case`，但须在 spec 扉页并列中文名。

### 1.2 产出边界
本阶段唯一固定产出为：`{DOC_DIR}/solutions/SOLUTION-{IDEA-ID}.md`。
- **定位**：用于**共识级**范围、目标、影响、冲突化解与交付计划。
- **非目标**：不替代 PRD、ADD 或详细测试设计。
- **下游分工**：
  | 下游技能 | 职责 |
  |----------|------|
  | **sdx-analysis** | 需求深化、MVP 清单与验收要点 |
  | **sdx-prd** | PRD、用户故事与详细功能需求 |
  | **sdx-design** | 架构设计（ADD）、规约与实现细节 |

## 2. 设计原则

### 2.1 模板驱动
必须严格遵循 [solution-template.md](../assets/solution-template.md) 的**七章**结构。不得删除章节，无内容处标注「不适用」或「待补充」。

### 2.2 业务可读
正文必须使用业务语言。核心准则：用「谁能做什么」「流程如何变」代替系统内部构造、接口或表名。

### 2.3 证据优先
影响面评估与冲突分析必须引用 `knowledge/` 或工程事实，禁止凭空臆测。
- **引用格式**：`BC-001 实体名` (知识库)、`文件名 §章节` (文档)、`类:方法` (代码)。
- **注意**：证据仅用于 Agents 内部分析，写入文档正文时需转写为业务表述。

### 2.4 按需加载
仅读取当前步骤必需的文件（原始描述 -> 核心知识库 -> 规约 -> 方案）。严禁通读全库。

### 2.5 歧义标注与决策阈值
对业务描述中的歧义、矛盾或缺失，标注为 **Q-n**。
- **暂停阈值**：歧义项 > 3 且涉及核心目标 -> 停止执行，输出待澄清清单。
- **预留阈值**：歧义项 ≤ 3 且不涉及核心目标 -> 在 §5.2 标注后继续。

### 2.6 可追溯性要求
- **G-n**：必须可追溯到原始业务描述的具体段落。
- **影响点**：必须可追溯到具体业务能力或协作环节。
- **C-n**：必须追溯到具体业务规则、流程约定或业务后果。
- **R-n**：必须追溯到冲突分析或方案取舍过程。

## 3. ID 编号规范

所有编号在文档内必须连续、无重复、无断号。

| 前缀 | 用途 | 示例 |
|------|------|------|
| `SOLUTION-{IDEA-ID}` | 文档/方案编号 | `SOLUTION-260412-总部直营政策` |
| `G-{n}` | 业务目标 (Goal) | `G-1`, `G-2` |
| `Q-{n}` | 待澄清问题 (Question) | `Q-1`, `Q-2` |
| `C-{n}` | 冲突或协作影响 (Conflict) | `C-1`, `C-2` |
| `R-{n}` | 风险 (Risk) | `R-1`, `R-2` |

## 4. 反模式清单（禁止项）

| 类型 | 描述 |
|------|------|
| **技术语言入正文** | 在正文中使用接口名、表名、中间件等技术术语 |
| **臆测影响面** | 未引用 knowledge 或事实即声称受影响 |
| **吞没歧义** | 自行补全不明确需求而不标注 Q-n |
| **范围蔓延** | 直接编写用户故事级细则或技术设计 |
| **模板调章** | 跳过、重排或删除模板规定的章节结构 |
| **通读全库** | 无目的性地一次性读取大量不相关文件 |
| **无编号引用** | 目标/冲突/风险无统一编号，导致链条断裂 |
| **单方案定论** | 多路径可选时不对比，直接给出唯一结论 |
| **空章提交** | 章节下无内容且未标注状态说明 |
| **跳过 Spec 闸门** | 未完成中间 spec 用户确认即生成 SOLUTION 文档 |

## 5. 最佳实践

- **需求提取**：标注每条需求性质（功能/非功能）、类型（新增/变更/修复）及优先级（P0–P3）。
- **影响评估**：沿业务流程/协作链追踪间接影响，从用户感知、数据完整、业务连续三个维度标注程度。
- **冲突化解**：为每个冲突提供至少一个化解方案，高严重度冲突提供备选方案。
- **MVP 拆分**：按**独立业务价值**拆分，确保每个 MVP 可独立演示。依赖方向必须单向（N+1 可依赖 N）。

---

## 6. 错误处理

- **描述模糊**：暂停并请求用户澄清（Q-n）。
- **知识库缺失**：发出警告，标注「分析盲区」后基于已知信息继续。
- **冲突无法化解**：记录为高风险（R-n），列出利弊并提请升级决策。
