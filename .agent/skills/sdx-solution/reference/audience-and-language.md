# 受众与文档语言（sdx-solution）

主要读者为**业务方与产品经理**。正文用「谁能做什么、流程如何变、验收与对外承诺是什么」来表述，而不是系统内部如何调用。

---

## 正文宜写 / 宜弱化

| 宜写入正文（业务语言） | 宜弱化或避免（留给下游技术设计） |
|----------------------|-------------------------------|
| 角色、场景、业务流程 | 类名、接口名、方法名 |
| 业务规则、异常与边界（业务话术） | 表名、字段名、消息队列/缓存等中间件名 |
| 成功标准、业务价值、MVP 边界 | 具体技术栈、框架、部署形态 |
| 协作依赖（与哪个团队/环节对齐） | 服务模块名、协议类型（REST/gRPC 等） |

---

## 转写示例

| 技术表述（避免） | 业务表述（推荐） |
|----------------|----------------|
| 「调用 FeeAppealService.create() 接口」 | 「提交费用申诉后，系统自动进入审核队列」 |
| 「写入 appeal_record 表」 | 「申诉记录将被保存，可供后续查询与追溯」 |
| 「通过 Kafka 异步通知下游」 | 「审批结果将在 5 分钟内通知相关协作方」 |
| 「P99 延迟 < 200ms」 | 「高峰时段操作仍须流畅，须与研发共拟可度量指标」 |

---

## Agent 转写要求

Agent **可以**查阅 `knowledge/`、`knowledge/technical/`、INDEX_GUIDE 等核对事实；写入 `SOLUTION-*.md` 时**必须**将工程事实转写为业务表述。

确需保留的技术线索（如系统边界、集成约束）集中放入 **§7.3 内部参考**，并标注「待研发确认」。
