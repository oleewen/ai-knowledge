# 解决方案检查清单与语言规范（sdx-solution）

本文档合并了受众语言要求与质量验收标准。它是步骤 5（文档输出与评审）的强制性依据。

---

## 一、受众与语言规范

解决方案文档面向**业务方与产品**，用于立项前对齐。**禁止**在正文中使用工程/技术内部实现术语。

### 1. 语言转写规则
将技术事实转写为「谁能做什么」或「业务结果」。

| 业务描述（✅ 准入） | 技术实现（❌ 禁入正文） |
|----------------------|--------------------------|
| 快递网点操作员可以发起申诉 | 调用 PolicyAppealApi.create 接口 |
| 审核结果在 2 小时内同步给申请方 | 通过 MQ 消息异步推送审核结果 |
| 申诉单提交后 24 小时未操作自动作废 | 定时任务扫描 policy_appeal 表状态 |
| 申诉流程分三个阶段：提交→审核→结算 | 状态机：DRAFT→SUBMITTED→SETTLED |

### 2. 严禁出现的关键词
- **技术栈**：Spring Boot, Kafka, Redis, TiDB, Dubbo, HTTP/RPC 等。
- **工程细节**：接口名、方法名、类名、数据库表名、字段名。
- **例外**：若需保留技术追溯线索，**必须**放入 §7.3「内部参考（仅供研发接力）」，并标注「待研发确认」。

## 二、质量自查清单（QA Checklist）

对已达标条目，在 `SOLUTION-*.md` 的 §7.4 中将 `- [ ]` 改为 `- [x]`。

### 1. 完整性（Completeness）
- [ ] **章节完备**：## 1 至 ## 7 章节齐全，无实质内容的小节须标明「不适用」。
- [ ] **目标可度量**：§1.3 的 G-n 必须包含可验证的成功指标（如「RT 降低 20%」）。
- [ ] **范围清晰**：§2.3 明确界定 In/Out 边界。
- [ ] **影响四维度**：§3 覆盖功能、数据、接口（对外承诺）、下游四个维度。
- [ ] **冲突闭环**：§3.4 必须显写「无冲突/不适用」或列出 C-n 及化解方案。
- [ ] **决策透明**：§4.3 阐明推荐方案的核心逻辑、备选方案及取舍理由。

### 2. 逻辑与追溯（Traceability）
- [ ] **编号追溯**：G-n（目标）、Q-n（疑问）、C-n（冲突）、R-n（风险）编号在全文自洽。
- [ ] **依赖流转**：交付计划（§6）中的 MVP 拆分符合业务交付价值，无循环依赖。
- [ ] **一致性**：方案（§4）能直接支撑目标（§1.3）并覆盖所有范围内需求（§2.3）。

### 3. 文档规范（Standards）
- [ ] **元数据合规**：文末包含 fenced `yaml` 格式元数据，id 与文件名匹配。
- [ ] **无 YAML 头**：文件开头禁止出现 `---` 引导的 YAML frontmatter。
- [ ] **专业性**：删除所有占位符、提示词或 Agent 内部思考日志。

## 三、发布前自查（Audit）
在提交前通读全文，回答以下问题：
1. 业务方能否在不理解代码的前提下看懂本文？
2. 是否所有 R-n（风险）都有应对措施？
3. 是否所有 Q-n（待澄清）都已在 §5.2 登记状态？
