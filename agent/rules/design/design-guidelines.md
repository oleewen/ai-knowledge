# 设计规范指南

> **结论**：目标工程设计按 DDD + 整洁/六边形边界评审；门禁与术语编码见下文。  
> **范围**：按需启用（非本仓 Markdown 知识库默认约束）。六边形模块落盘见 [project-structure.md](../coding/project-structure.md)。

## 核心设计原则

### 领域驱动设计（DDD）

- 统一语言 · 限界上下文 · 聚合根 · 领域事件

### 架构

- 整洁 / 六边形：业务核心独立于框架与工具（模块树 → [project-structure.md](../coding/project-structure.md)）
- 分层依赖清晰；读写分离（CQRS）按需

### 设计模式

SOLID · KISS · DRY · YAGNI（不在此复述教科书定义）

## 设计评审标准

### 完整性

正确 · 完备（含边界）· 异常闭环

### 健壮性

安全 · 容错 · 稳定（高并发/可用）· 一致与幂等

### 质量属性

可扩展 · 可维护 · 可测试 · 可部署（CI/CD）

## 文档规范

### 必出图

| 类型 | 用途 |
| --- | --- |
| 概念/业务模型 | 关键实体关系 |
| C4 系统/模块 | 应用架构与依赖 |
| 数据流 | 核心业务数据流转 |
| 类图 / 时序 / 状态 / ER | 领域、交互、状态、表关系 |

图用 Mermaid；与代码同仓 Git 维护，决策与权衡可追溯。

### 术语定义

| 术语 | 含义 | DDD对标 | 数字编码 | 示例 |
| ---- | ---- | ---- | ---- | ---- |
| 业务流程 | 实现目标的完整业务活动序列 | 限界上下文 | a.b（两位） | 商品发布、申诉处理 |
| 业务活动 | 具体操作，对应 API 能力 | 应用服务 | a.b.c（三位） | 创建商品、提交申诉 |
| 业务任务 | 活动的原子工作单元 | 领域服务 | a.b.c.d（四位） | 验证商品、计算申诉金额 |
| 业务步骤 | 任务执行步骤 | 领域服务方法 | a.b.c.d.e（五位） | 检查库存、验证资格 |
| 业务规则 | 约束行为的规则 | 业务规则 | a.b.c.d.e.f（六位） | 库存>0、申诉额≤订单额 |

## 实施指南

### 设计流程

1. 需求分析（含约束）
2. 领域建模（聚合/实体/值对象）
3. 接口契约
4. 逻辑与数据模型
5. 技术选型
6. 评审验证

### 质量门禁

- 设计评审通过
- 代码覆盖率 ≥80%
- 性能指标达标
- 安全扫描通过

## 设计验证

### 综合检查清单

#### 业务分析

- [ ] 业务名词有定义与统一语言
- [ ] 流程覆盖场景含异常分支
- [ ] 领域模型符合 DDD，聚合边界清晰
- [ ] 业务能力完整，与实现解耦

#### 技术设计

- [ ] 架构符合六边形/整洁（见 project-structure）
- [ ] API 契约清晰（含协议需求）
- [ ] 逻辑模型反映分层与领域关系
- [ ] 数据模型与领域模型一致

#### 非功能

- [ ] 性能符合 SLA
- [ ] 安全满足业务要求
- [ ] 可扩展 / 可维护 / 可测试

#### 文档

- [ ] 图表用 Mermaid
- [ ] 数字编码贯穿流程到实现
- [ ] 格式统一、内容完整
- [ ] 本清单项已核对
