# Gotchas — 已知陷阱与防错指南

## 1. 锚点匹配失败

**问题**：GitHub Markdown 锚点规则与直觉不符。全角括号（）、斜杠 `/` 等字符会被直接删除，而非转为 `-`，导致手动拼写的锚点与实际生成的锚点不一致，`get_section_content` 返回空字符串。

**防错措施**：脚本同时尝试两种锚点格式——GitHub 规则（删除标点）和旧规则（合并连续 `-`），任意一种匹配即视为命中。

**排查方法**：当 `get_section_content` 返回空字符串时，手动验证锚点格式；可查看 `/tmp/keyword_tag_cache.json` 了解扫描到的文件和章节情况。

---

## 2. YAML 附录重复追加

**问题**：直接追加而非替换会导致文件末尾出现多个 `<!-- spec-tags -->` 块，破坏文档格式，且后续读取时只能匹配到第一个块。

**防错措施**：`write_tags_to_file` 先用正则删除旧块（包含前面的 `---` 分隔线）再追加新块，保证操作幂等。

**排查方法**：检查文件末尾是否有多个 `---` 分隔线；若出现，手动删除多余块后重新运行即可恢复。

---

## 3. 扫描目录排除规则

**问题**：若不排除目标文件所在子目录，目标文件自身的内容会被纳入候选词统计，污染结果（种子词在目标文件中出现频率极高，导致无关词被误选）。

**防错措施**：`find_relevant_sections` 动态计算目标文件所在直接子目录名并在 `os.walk` 的 `dirs` 过滤中排除。

**注意**：排除的是直接子目录名（如 `overview`），不是完整路径；若目标文件直接位于 `--scan-dir` 根目录下，则不排除任何子目录。

---

## 4. `--selected` 参数格式

**问题**：`--selected` 接收逗号分隔的词语列表，词语间若有多余空格会被当作词语的一部分，导致写入的关键词含有前导/尾随空格。

**防错措施**：脚本在解析时会对每个词语执行 `strip()`，轻微空格问题可自动处理。

**注意**：候选词提取规则（中文词组 / 英文术语）本身不会产生含逗号的词语，因此逗号歧义问题在实践中不会出现。

---

## 5. `--phase 2` 前未执行阶段 1

**问题**：直接执行阶段 2 时，目标文件末尾没有 `<!-- spec-tags -->` 块，脚本读取不到关键词，报错退出。

**防错措施**：Skill 层在 `phase all` 时保证先执行阶段 1 再执行阶段 2；单独执行 `--phase 2` 时若报错，提示用户先执行阶段 1。

**排查方法**：检查目标文件末尾是否存在 `<!-- spec-tags` 块；若不存在，先运行 `--phase 1-scan` + `--phase 1-write` 写入关键词。

---

## 6. 副标题列链接解析

**问题**：表格行以 `|` 分割后，`parts[0]` 为空字符串（行首 `|` 前的空内容），因此副标题列的实际索引是 `parts[2]` 而非 `parts[1]`，容易写错导致解析到错误列。

**防错措施**：`extract_link_from_cell` 只提取第一个 Markdown 链接，忽略单元格内其他内容，降低误解析概率。

**注意**：若表格列数少于 3（即 `len(parts) < 3`），该行会被跳过，视为不相关行。

---

## 7. 向后兼容的 `--phase 1` 在非终端环境下挂起

**问题**：`--phase 1` 内部调用 `input()` 等待用户在终端输入编号，在 CI、管道或 Kiro Skill 环境中没有 TTY，进程会无限期挂起。

**防错措施**：Skill 层始终使用 `1-scan` + `1-write` 子命令，完全绕过交互式 `input()`，不调用 `--phase 1`。

**注意**：`--phase 1` 和 `--phase all` 仅供开发者在本地命令行直接使用，不在 Skill 自动化工作流中出现。
