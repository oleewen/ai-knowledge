# sdx-feature 核心概念

本文件定义 FEATURE 的编号与内容约束；章骨架见 [模板](../assets/feature-template.md)，推进授权见 [gates.md](gates.md)。

## IDEA-ID

继承上游 ANALYSIS 的 IDEA-ID，不另起同主题编号。新链遵循 `{YYMMDD}-{主题}`（中文短名 2–6 字）；已有 ASCII slug 保留，并在正文注明中文题名。

| 产物 | 路径 |
| --- | --- |
| 上游 | `{DOC_DIR}/analysis/ANALYSIS-{IDEA-ID}.md` |
| 本阶段 | `{DOC_DIR}/features/FEATURE-{IDEA-ID}.md` |
| 下游 PRD | `{DOC_DIR}/requirements/REQUIREMENT-{IDEA-ID}/MVP-Phase-{N}/PRD-{IDEA-ID}-{N}.md` |

文首 frontmatter 字段以模板为准；`id` 等于文件名去掉 `.md`，`parent` 为同 IDEA-ID 的 ANALYSIS。

## 编号

| 编号 | 定义与追溯 |
| --- | --- |
| `G-n` | §1.2 目标，对齐上游目标 |
| `FR-nnn` | §2 功能需求，关联 G-n |
| `BR-nnn` | 所属 FR 内的业务规则 |
| `R-n` | §5 风险，指向依赖或影响 |
| `M{n}（短名）` | 上游 §6.1 里程碑，概览原样引用 |
| `MVP{n}（短名）` | §4 交付版本，装载 FR |
| `Q-n` | 当前段待澄清问题，不是技术决策编号 |

编号保持唯一、连贯；跳号须说明。`G-n` 不是流程门禁编号。

## 概览与 FR

主料为 ANALYSIS §6.1「覆盖范围」，场景与 In Scope 用于补漏。每个 FR 同时满足**可独立验收、一 FR 一业务模块**；跨模块先按职责拆，再按可验收性拆。支撑项随消费方能力，不虚构独立业务价值。

| 概览列 | 约束 |
| --- | --- |
| 需求编号 | 唯一 FR 编号，与正文一一对应 |
| 需求名称 | 非空，≤30 个 Unicode 码点；等于 `### FR-nnn: 名称` 中的名称 |
| 需求概要 | 非空，一句话能力，≤60 个 Unicode 码点；不塞规则或验收 |
| 优先级 | 按成功标准和 In Scope 关键性判断，与里程碑顺序解耦 |
| 所属模块 | 非空，单一业务能力域短名；不能是工程分层或多模块列表 |
| 所属里程碑 | 上游原样 `M{n}（短名）`，一 FR 一个；不写 `MVP{n}` |
| 关联目标 | 可追溯到 §1.2 G-n |

长度含空格与标点。模块清单优先取自知识库索引/overview；缺失时与用户共拟并归一，不编造已存在的实体。名称、概要、正文均不得越出所属模块职责；模块归属只在概览列维护。

每个 FR 按模板写描述、输入、处理逻辑（BR）、业务对象、输出、异常与边界、验收标准。§2 收口核对编号集合、标题名称、目标与正文语义。

## 里程碑与 MVP

§4 才将 FR 装入 `MVP{n}（短名）`，可跨里程碑拆分或合并。每个 FR 恰好归属一个 MVP；§4.1 为装载清单，§4.2 展开同一归属，不能重复计作第二次装载。

每个 MVP 应有可交付业务价值；基础依赖随首个消费方交付。MVP 数量建议接近里程碑数，允许按实情偏离但须解释；这不是固定数量门槛。§4.3 依赖必须无环。

## `--depth`

| 值 | 差异 |
| --- | --- |
| `quick` | 压缩研究与说明，优先细化 P0/P1 和关键风险；明确未展开部分，不丢已确认 FR |
| `standard` | 默认六章完整粒度 |
| `deep` | 加强规则、交付取舍、依赖和风险分析，仍使用业务表述 |
