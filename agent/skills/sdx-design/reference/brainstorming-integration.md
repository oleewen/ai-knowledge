# brainstorming 嵌入层（sdx-design）

说明阶段二如何在门禁 **Gd{n}**（DSD §1–§4）内嵌入 brainstorming 节奏，以及与独立 `/brainstorming` 的差异。

---

## 与独立 `/brainstorming` 的差异

| 维度 | 独立 `/brainstorming` | 本技能内嵌（阶段二） |
|------|----------------------|----------------------|
| 主产物 | 常为 `*-design.md` + `writing-plans` | 会话 spec：`...-sdx-design.md`；终稿：`DSD-*.md` |
| 正常终态 | 进入 `writing-plans` 等实现计划 | **Qclose-1** → 阶段三分块定稿 |
| HARD-GATE | 以 brainstorming 技能为准 | **仍以 sdx-design HARD-GATE 为准** |

**禁止**：在仅执行 `/sdx-design` 的对话中，用「已完成 brainstorming」为由跳过 **Gd{n}** 收口、门禁标记或 Qclose-1；也**禁止**默认创建独立 `*-design.md` 替代本会话 spec。

若用户明确需要独立产品/架构讨论 spec，应**另开会话**执行 `/brainstorming`，再在后续会话用本技能消费其结论。

---

## Gd{n} 内多方案子流程

**触发**：当前门禁的结论依赖两条及以上真实可选路径（接口风格、数据模型、规约拆分等；架构级选型一般在 **`/sdx-architect`（Ga1–Ga2）**）。

**节奏**（仍在同一 **Gd{n}** 内，未收口前）：

1. 列出 **2–3 套**路径，**语义命名**（避免空洞的「方案A/B」）
2. 给出利弊、适用条件、推荐及理由
3. 用标准四选项收口，结论写入 spec「本门禁结论」，注明被选方案及未选方案的搁置理由

**与 Q-n 的分工**：Q-n 解决**信息缺口**；本节解决**信息足够但决策分叉**。若分叉内仍有事实缺口，先收敛 Q-n，再回到方案对比。

---

## 各门禁典型触发（非穷尽）

| 门禁 | 可能出现的「多套方案」示例 |
|------|--------------------------|
| Gd1（§1） | 设计概述与 ASD §1 的表述粒度、优先级口径、约束摘取方式 |
| Gd2（§2） | API 风格、幂等与一致性策略、缓存策略、DDL 取舍 |
| Gd3（§3） | 规约目录拆分、YAML 粒度、`source` 指向、需求规约表列项 |
| Gd4（§4） | 附录深度、对外文档引用级别、术语表范围 |

**Gd2** 常为多方案密集区，但不限于此：只要当前 **Gd{n}** 的结论依赖方案选择，就应在本门禁内完成对比再收口。
