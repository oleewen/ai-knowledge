# sdx-design 工作流规范

[SKILL.md](../SKILL.md) 为主干。本文件补充：**门禁状态机**（回跳影响面、Q-n 协议）与**阶段三内容生成算法**（原四步）。

---

## 门禁状态机

```
[阶段一：参数确认]
    ↓ 全部参数确认（或 S/F 跳过）
[阶段二：逐门禁交互]
    全量 5G：G1 → G2 → G3 → G4 → G5
    精简 3G：G(1–2) → G3 → G(4–5)
    每门禁：草案呈现 → （可选）多方案对比 → 确认点逐一确认 → 门禁收口
    ↓ 全部门禁收口（或 S/F 跳过）
[Qclose-1 总确认]
    ↓ C / S（PENDING → CONFIRMED）
[阶段三：文档生成]
    骨架 → chunk 1–5（或精简 3 chunk）→ 规约 YAML → 终检
```

---

## 回跳影响面评估

用户回跳到 G{k} 并修改结论后，评估后续门禁的依赖类型：

| 依赖类型 | 判断标准 | 处理方式 |
|---------|---------|---------|
| 强依赖 | 后续门禁与 G{k} 新结论显式矛盾，或引用同一实体（同一 DD-n/API-n、服务/数据边界） | 须重新确认 |
| 弱依赖 | 后续门禁大量引用 G{k} 的术语、范围或验收表述 | 建议重新确认 |
| 无依赖 | 后续门禁内容与 G{k} 无关联 | 保持已确认状态 |

**典型示例**：回跳 G2 变更服务切分 → G3 API 与 G4 规约路径往往为强依赖；回跳 G1 改设计目标 → G2–G5 多需至少弱依赖重审。向用户说明影响面后，由用户选择「仅强依赖重走」或「强弱一并重走」。

## 待澄清项（Q-n）协议

**触发**：阶段二任意门禁中出现歧义、矛盾或信息缺失时，立即标注 Q-n。

**格式**：

```
Q-{n}：{问题描述}

背景：{为什么需要澄清，影响哪个决策}

选项：
1. {具体含义描述}（推荐）
2. {具体含义描述}
3. 其他（请说明）

请选择：C / M / S / F
```

**规则**：
- 每次只提一个 Q-n，等用户回答后再提下一题
- 选项描述具体含义，不写「方案A/方案B」等抽象标签
- 澄清结论写入对应 ADD 草案条目，不单独设与交付物无关的「待澄清问题」章
- 用户选 S 时，在 spec 中标注「Q-{n} 待澄清」并说明影响范围

## 阶段三内容生成算法（四步）

**仅在用户总确认（`CONFIRMED`）之后**用于填充 ADD 与规约，不得绕过 HARD-GATE 单独执行。

### 步骤 1：架构设计（→ §1–§2）

**输入**：PRD + 需求分析（当前 MVP 章节）+ `knowledge/technical/`（按需）+ `knowledge/business/`（按需）

**五维度**：

| 维度 | 设计内容 | 输出位置 |
|------|---------|---------|
| 系统架构 | 服务变更、调用关系、变更范围 Mermaid 图 | §2.1 |
| 接口协议 | 接口名称、所属服务、能力说明、输入输出概要 | §2.2 |
| 领域模型 | 聚合根/实体/值对象、领域事件（名称、触发条件、携带数据、消费者） | §2.3 |
| 数据架构 | ER 图、表设计概要（新增/变更）、分片设计、数据迁移方案 | §2.4 |
| 发布方案 | 发布步骤、发布检查、回滚方案 | §2.5 |

**关键设计决策**：编号 DD-{NNN}，记录决策点、决策结果、决策理由、备选方案，关联 PRD 的 US-n / FR-n。

**depth 影响**：`quick` 仅系统架构 + 接口协议；`standard` 完整五维度；`deep` 增加性能建模（QPS/TPS 估算）、容量规划、灾备方案。

---

### 步骤 2：详细设计（→ §3）

**输入**：步骤 1 产出 + PRD 用户故事与业务规则 + 现有代码结构（按需）

1. **应用架构**（§3.1）：容器级架构图，标注 MQ、异步处理、定时任务等机制
2. **API 详设**（§3.2）：编号 API-{NNN}，含签名、参数、响应、错误码、幂等性、容错策略
3. **业务逻辑**（§3.3）：核心类图（DDD 分层）、状态机、时序图 + 伪代码、一致性策略（编号 LOGIC-{NNN}）
4. **数据访问**（§3.4）：DDL（含 `gmt_create`/`gmt_modified`）、索引策略、分页策略、缓存策略
5. **非功能**（§3.5）：安全设计（认证授权、数据脱敏、审计日志）、可观测设计（日志、监控、链路追踪）

**depth 影响**：`quick` API 仅签名与参数，跳过伪代码与缓存策略；`deep` 增加性能基准测试方案、压测策略、全链路追踪设计。

---

### 步骤 3：规约生成（→ specs/）

从步骤 1–2 产出按服务提取，写入：

```
specs/{service-name}/
├── api/        ← 从 §3.2 提取
├── domain/     ← 从 §2.3 提取
├── data/       ← 从 §3.4 提取
└── integration/ ← 从 §2.1 提取
```

每个规约文件头部须标注 `source`（ADD 章节，如 `ADD §3.2 API-001`）与 `requirement`（如 `FR-001`）。

---

### 步骤 4：文档输出与终检（→ ADD-*.md）

1. 将步骤 1–2 产出按 [../assets/add-template.md](../assets/add-template.md) 五章结构整合
2. 填充文末元数据（`## 文档元数据` 下 fenced yaml，**禁止**文件头 frontmatter）：
   - `id`、`title`、`version`、`status: draft`、`created`、`updated`、`parent`（PRD 编号）、`mvp_phase`
3. 对照 [quality-checklist.md](quality-checklist.md) 逐项判定，已达标项改为 `- [x]`，未达标保持 `- [ ]`

**输出目录**：

```
{DOC_DIR}/requirements/REQUIREMENT-{IDEA-ID}/MVP-Phase-{N}/
├── ADD-{IDEA-ID}-{N}.md
└── specs/{service-name}/{type}/*.yaml
```

## 步间数据流

```
步骤 1 → §1 设计概述、§2 架构设计
步骤 2 → §3 详细设计
步骤 3 → specs/ 规约文件、§4.1 参考文档（规约路径列表）
步骤 4 → 完整 ADD 文档 + specs/
```
