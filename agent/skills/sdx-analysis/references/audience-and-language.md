# 受众与文档语言（sdx-analysis）

主要读者为**产品经理、需求分析师**与参与范围评审的**业务方**。正文用「谁能做什么、规则如何、如何验收、与谁协作」来表述，而不是系统内部如何调用。

语言原则与转写示例与 sdx-solution 完全一致，见 [../../sdx-solution/references/audience-and-language.md](../../sdx-solution/references/audience-and-language.md)。

---

## 正文宜写 / 宜弱化

| 宜写入正文（产品/需求语言） | 宜弱化或避免（留给下游技术设计） |
|---------------------------|--------------------------------|
| 角色、场景、用户故事或主流程 | 类名、接口名、方法名 |
| 业务规则、异常与边界（业务话术） | 表名、字段名、消息队列/缓存等中间件名 |
| 验收标准、优先级、MVP 边界 | 具体技术栈、框架、部署形态 |
| 协作依赖（与哪个团队/环节对齐） | 服务模块名、协议类型（REST/gRPC 等） |

---

## Agent 转写要求

Agent **可以**查阅 `knowledge/`、`knowledge/technical/`、INDEX_GUIDE 等核对事实；写入 `ANALYSIS-{ID}.md` 时**必须**将工程事实转写为**场景、规则、验收与协作**表述。

确需保留的技术线索集中放入 **§6.3 变更历史**，并标注「待研发确认」。

---

## 与 sdx-solution 的差异

| 维度 | sdx-solution | sdx-analysis |
|------|-------------|-------------|
| 主要读者 | 业务方与产品经理 | 产品经理与需求分析师（业务方参与范围评审） |
| 正文粒度 | 业务目标、影响面、方案思路 | 功能需求（FR）、业务规则（BR）、验收标准、MVP 拆分 |
| 技术线索归宿 | §7.3 内部参考 | §6.3 变更历史 |
| 非功能表述 | 不涉及 | 优先用户可感知表述；量化指标写「须与研发共拟」 |
