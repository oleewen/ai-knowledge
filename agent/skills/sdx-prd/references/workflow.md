# sdx-prd 工作流

[SKILL.md](../SKILL.md) 为主干；写入类门禁与例外见 [gates.md](gates.md)。

---

## 目标

在**需求分析（ANALYSIS）**与**当前 MVP** 范围内，产出可评审、可验收的 **PRD**（十一章），为下游 **ASD / DSD** 提供可追溯的 US/UC/FR/BR/AC 锚点。

---

## 核心约束（执行须满足）

| 约束 | 说明 |
|------|------|
| 模板驱动 | 严格遵循 `prd-template.md` 十一章；无内容章节保留标题并标注「不适用」 |
| 证据优先 | 用户故事与业务规则须引用 FR-n / BR-n，禁止臆测 |
| MVP 聚焦 | 仅覆盖 `--mvp` 对应范围，不混入后续 MVP |
| 业务可读 | 正文以产品/业务语言为主；细则见 [audience-and-language.md](audience-and-language.md) |
| 歧义标注 | 不确定项标为待澄清，暂停确认，禁止自行假设 |
| 可追溯 | US-n→FR-n，UC-n↔US-n，BR-n 与 ANALYSIS 一致，AC/NAC 可指回 US 或 §9 |
| 命名约定 | `{DOC_DIR}/requirements/REQUIREMENT-{IDEA-ID}/MVP-Phase-{N}/PRD-{IDEA-ID}-{N}.md` |

完整原则、FR 句式、表格级反模式与错误处理见 [design-principles.md](design-principles.md)；叙事级反模式见 [anti-patterns.md](anti-patterns.md)。

## 阶段一：准备工作

**一次性**抛出以下参数供用户选择（支持快捷修改，如 `1.1 M IDEA-ID=XXX`）：

1. **IDEA-ID 主题** — 默认 `{YYMMDD}-{中文主题}`；须与上游 `ANALYSIS-{IDEA-ID}.md` **对齐**（见 [core-concepts.md](core-concepts.md)）。
2. **MVP 阶段编号 `N`** — 对应 `MVP-Phase-{N}` 与终稿文件名 `PRD-{IDEA-ID}-{N}.md`。
3. **门禁粒度** — 3.1 全量 **11G（G1–G11）**（与 prd-template 十一章一一对应）；3.2 **精简 6G**：G(1)–G(6)（映射见下文「精简 6 门禁映射」）。
4. **分析深度** — 4.1 `standard`（默认）；4.2 `quick` 压缩叙述版；4.3 `deep` 含对标与交互细化要点。

**硬输入**：`{DOC_DIR}/analysis/ANALYSIS-{IDEA-ID}.md` 中当前 MVP 章节；不存在时终止，提示先执行 `sdx-analysis`。

## 阶段二：草稿确认

**路径**：`docs/superpowers/specs/YYYY-MM-DD-<topic>-sdx-prd.md`，骨架见 [../assets/prd-session-spec-template.md](../assets/prd-session-spec-template.md)。

### 标准四选项

每个门禁末尾附上（全文见 [gates.md](gates.md) 内 fenced 块）：C / M / S / F。

### 门禁与模板映射（全量 11G）

| 门禁 | 覆盖模板 | 状态 | 备注 |
|------|----------|------|------|
| [G{n}](#g{n}-XX) | [§{n} XX](#g{n}-XX) | 草案/已确认 | 示例行；按需复制为 G{n+1} |

**精简 6G** 映射见下文「精简 6 门禁映射」。

**会话草稿「门禁进度」表**：门禁列与覆盖模板列均须为指向**本会话 spec 稿内** `## Gn` 小节锚点。占位与示例见会话模板「门禁进度」。

### 门禁节奏（强制）

- 每次只呈现一段草案或一个待确认点，末尾附标准四选项。
- Gn 未收口前不展开 G(n+1)（回跳除外）。
- 进入本阶段后，**禁止**以「已在 `…/specs/….md` 中补充 G{n} 草案，要点如下：」起首；直接给出要点或提问。
- 回跳到 G{k} 后，按强/弱依赖评估后续门禁是否需重审（见「回跳影响面评估」）。

### brainstorming 嵌入层（阶段二）

阶段二在门禁交互上**对齐** brainstorming 的可复用节奏，但以本会话 spec 与 `PRD-*.md` 为唯一交付主线。细则见 [brainstorming-integration.md](brainstorming-integration.md)。

- **单题澄清**：与 **Q-n** 协议一致（见「待澄清项（Q-n）交互协议」）。
- **任意 G{n} 内多套可取舍方案**：当存在两条及以上真实可选路径时，**须在本门禁内**先完成 brainstorming 式对比（2–3 套、业务语义命名、利弊与推荐），再写入「本门禁结论」并收口该 Gn。

### 总确认（Qclose-1）

规则与确认人见 [gates.md](gates.md)。

## 阶段三：草稿定稿

**3.1 骨架**：在 `{DOC_DIR}/requirements/REQUIREMENT-{IDEA-ID}/MVP-Phase-{N}/` 下新建 `PRD-{IDEA-ID}-{N}.md`，按 [../assets/prd-template.md](../assets/prd-template.md) 落十一章标题、表架、§11.3（`- [ ]`）、文末 fenced yaml；标注「草稿填充中」。

**3.2 分块填充**（默认 11 chunk，与 G1–G11 / §1–§11 对齐；精简 6G 时可用 6 chunk）：

| Chunk | 覆盖章节 | 填充要点 |
|-------|---------|---------|
| 1 | §1 产品概述 | 引用 SOLUTION/ANALYSIS/MVP；摘录成功标准与角色 |
| 2 | §2 业务流程 | 主流程 Mermaid + 步骤表（六要素）；EX-n 清单；跨系统时序 |
| 3 | §3 产品交互 | 交互旅程或说明；关键校验与反馈 |
| 4 | §4 用例模型 | 用例图（覆盖角色）；UC-n 含前后置、主成功场景、扩展场景 |
| 5 | §5 用户故事 | 每 FR-n 至少一 US-n；Given-When-Then 含正常+异常 |
| 6 | §6 功能模块 | 按业务能力域划分；模块与 US-n 对应 |
| 7 | §7 业务规则 | BR-n 集中汇总（触发条件、执行逻辑、优先级、关联用例） |
| 8 | §8 数据字典 | 业务术语；状态定义与流转 |
| 9 | §9 非功能需求 | 仅本 MVP 相关类别；指标/阈值 + 度量方法 |
| 10 | §10 验收标准 | AC-n 关联 US-n；NAC-n 与 §9 互链 |
| 11 | §11 附录 | §11.1 原型链接；§11.2 变更历史；§11.3 质量自查勾选 |

每块结束附标准四选项；用户可随时说「暂停」。

**终检**：对照 [quality-checklist.md](quality-checklist.md) 逐项判定，已达标项将 `- [ ]` 改为 `- [x]`，未达标项保持 `- [ ]`，禁止虚假勾选。

## 门禁状态机

```
[阶段一：参数确认]
    ↓ 全部参数确认（或 S/F 跳过）
[阶段二：逐门禁交互]
    全量 11G：G1 → G2 → … → G11
    精简 6G：G(1) → G(2) → … → G(6)
    每门禁：草案呈现 → （可选）多方案对比 → 待确认点逐一确认 → 门禁收口
    ↓ 全部门禁收口（或 S/F 跳过）
[Qclose-1 总确认]
    ↓ C / S（PENDING → CONFIRMED）
[阶段三：文档生成]
    骨架 → chunk 1 → … → chunk 11（或 6）→ 终检
```

### 精简 6 门禁映射

| 精简门禁 | 覆盖全量门禁 | 覆盖模板章节 |
|---------|------------|-------------|
| G(1) | G1 | §1 产品概述 |
| G(2) | G2、G3 | §2 业务流程、§3 产品交互 |
| G(3) | G4 | §4 用例模型 |
| G(4) | G5 | §5 用户故事 |
| G(5) | G6、G7、G8 | §6 功能模块、§7 业务规则、§8 数据字典 |
| G(6) | G9、G10、G11 | §9 非功能需求、§10 验收标准、§11 附录 |

## 回跳影响面评估

用户回跳到 G{k} 并修改结论后，评估后续门禁的依赖类型：

| 依赖类型 | 判断标准 | 处理方式 |
|---------|---------|---------|
| 强依赖 | 后续门禁与 G{k} 新结论显式矛盾，或引用同一 US/UC/FR/范围边界 | 须重新确认 |
| 弱依赖 | 后续门禁大量引用 G{k} 的术语、范围、优先级或验收表述 | 建议重新确认 |
| 无依赖 | 后续门禁内容与 G{k} 无关联 | 保持已确认状态 |

**典型示例**：回跳 G2（§2）改主流程 → G4 用例、G5 故事多为强依赖；回跳 G5 改故事拆分 → G6 模块、G10 AC 多为弱依赖。

向用户说明影响面后，由用户选择「仅强依赖重走」或「强弱一并重走」。

## G{n} 内多方案子循环

**触发**：当前门禁的结论依赖两条及以上真实可选路径时。详见 [brainstorming-integration.md](brainstorming-integration.md)。

**节奏**（仍在同一 G{n} 内，未收口前）：

1. 列出 2–3 套路径，**业务语义命名**（避免空洞的「方案A/方案B」）。
2. 利弊、适用条件、推荐及理由。
3. 用标准四选项收口，结论写入 spec「本门禁结论」。

**与 Q-n 的分工**：Q-n 解决**信息缺口**；本节解决**信息足够但决策分叉**。

---

## 待澄清项（Q-n）交互协议

**触发时机**：阶段二任意门禁中出现歧义、矛盾或信息缺失时，立即标注 Q-n。

**交互格式**：

```
Q-{n}：{问题描述}

背景：{为什么需要澄清，影响哪个决策}

选项：
1. {具体业务含义描述}（推荐）
2. {具体业务含义描述}
3. 其他（请说明）

请选择：C / M / S / F
```

**规则**：

- 每次只提一个 Q-n，等用户回答后再提下一题
- 选项描述具体业务含义，不写「方案A/方案B」等抽象标签
- 澄清结论写入对应 FR-n 或 US/UC 映射处，不单独设「待澄清问题」章
- 用户选 S 时，在 spec 中标注「Q-{n} 待澄清」并说明影响范围

## 各章节填充要点（阶段三参考）

### 前置：加载需求分析文档

1. 按 `--requirement` 定位 `{DOC_DIR}/analysis/ANALYSIS-{IDEA-ID}.md`；未指定时取最新 `ANALYSIS-*.md`
2. 从 §MVP 拆分方案中提取目标 MVP（`--mvp`）的 FR-n 清单、BR-n 清单、NFR 约束、角色列表
3. 定位产品愿景、成功标准（供 §1.2）；缺失时标「待澄清」，不阻断流程
4. **目标 MVP 章节不存在** → 终止，提示检查 MVP 编号

### §1 产品概述

- §1.1 引用 SOLUTION/ANALYSIS 路径与 MVP-Phase-{N}
- §1.2 从 ANALYSIS 摘录 SMART 成功指标；缺失标「待澄清」
- §1.3 本 MVP 范围 + Growth/Vision 后续阶段表（无则标「不适用」）
- §1.4 涉及角色与 §4 用例参与者保持一致

### §2 业务流程

- 主流程：Mermaid flowchart + 步骤表（步骤序号、参与角色、输入、处理逻辑、输出、业务规则 BR-n）
- 分支/异常：EX-n 清单（编号、描述、触发条件、处理方式、用户提示）；主流程与异常分开绘制
- 跨系统交互：Mermaid sequenceDiagram，标注同步/异步、超时处理；无则标「不适用」
- 业务规则**不内嵌**流程节点，在节点旁标注 `[BR-n]` 引用，汇总至 §7

### §3 产品交互

- 信息架构与操作路径（Mermaid journey 或 flowchart）
- 关键校验节点、成功/失败反馈；原型链接（如有）

### §4 用例模型

- 用例图（Mermaid graph）覆盖 §1.4 全部角色；标注 include/extend 关系
- 每个 UC-n：参与者、前置条件、后置条件、触发条件、主成功场景（≤9步）、扩展场景
- 确保 UC-n 与 US-n 双向映射

### §5 用户故事

- 当前 MVP 内每个 FR-n 至少一个 US-n；格式：「作为{角色}，我希望{功能}，以便{价值}」
- 每个 US-n：优先级（继承 FR-n）、关联 FR-n、关联 BR-n
- 验收标准：Given-When-Then，含正常场景 + 至少一个异常/边界场景
- INVEST 校验：可独立交付、可估算、可测试

### §6 功能模块

- 按**业务能力域**划分（非技术层次）；Mermaid graph 绘制模块关系
- 每个模块：职责、包含 US-n 列表、输入/输出、依赖模块

### §7 业务规则汇总

- 将 §2/§5 中散落的 BR-n 集中汇总；字段：规则编号、名称、触发条件、执行逻辑、异常处理、优先级、关联用例
- 存在互斥规则时显式说明冲突处理策略

### §8 数据字典

- §8.1 业务术语（术语、定义、示例）
- §8.2 状态定义与流转（实体、状态、可流转状态）；标注终态与非法转换拦截策略

### §9 非功能需求

- 仅写本 MVP 相关类别；每类给出指标/阈值 + 度量方法；无依据则标「待澄清」
- 参考类别：性能、可靠性、安全、合规、可观测性、兼容性等

### §10 验收标准

- §10.1 AC-n：关联 US-n，可测、无量词堆砌
- §10.2 NAC-n：与 §9 NFR 互链，显式标注「不适用」或对应 NFR 行

### §11 附录

- §11.1 原型/线框图链接
- §11.2 变更历史（初始版本）
- §11.3 质量自查：对照 [quality-checklist.md](quality-checklist.md) 逐项勾选
