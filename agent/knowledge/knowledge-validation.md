# 知识库统一校验规范

> **职责**：结构、确定性关系与必需引用的共同验收口径，以及事实核验、覆盖范围和兼容结果的表达。
> **边界**：文件格式见 [OKF](okf-spec.md)，身份见 [命名规范](naming-conventions.md)，层级与基数见 [治理规则](knowledge-governance.md)，关系见 [关系模型](entity-relations.md)，引用见 [引用规范](knowledge-reference-rules.md)。本文件定义校验契约，不替代这些语义真源。

## 校验入口与上下文

实体构建、修订和独立验证应使用同一套结构、确定性关系和必需引用校验；索引或可视化与输入一致，不能代替实体合规。事实真实性另列状态，不由格式检查推断。

每次校验须能定位以下上下文；沿用当前报告或会话记录，不强制新增日志文件或实体字段。

| 上下文 | 必需信息 |
| --- | --- |
| 逻辑层与文档根 | 已解析的知识层、仓库及 DOC_DIR；元库须明确选中层，不以 `docs` 等物理目录名推断层级 |
| 对象性质 | 模板/示例或业务实体；同一范围混合时分别列出 |
| 检查范围 | 文件、实体、视角、相关库及排除项；是否覆盖完整身份域和关系域 |
| 规则基线 | 规则所属版本及 commit；含未提交规则时记录实际规则内容哈希，不能只报分支名 |
| 源快照 | 已读实体、关系和引用目标对应的仓库、commit；未提交内容记录实际内容哈希，标明未读与不可读来源 |
| 身份上下文 | 实体类型、ID、已核实的 APP/MS 宿主、目标所属库及身份解析结果；多候选不得任取 |

局部批次可以证明已检查对象的局部断言，不得据此证明全局唯一、跨库反向完整或全量无入边。读取期间来源变化时，受影响断言重新核验或列为待核实。

## 统一检查

### 结构与身份

先按用途、稳定 ID 和实体树位置判型，再验证字段；不能因 `type` 拼错、缺失或未知而把应为实体的文件降为叙事、跳过校验。README/index 等真正的导航入口按自身规则检查，不强套实体 Profile。

实体须验证九字段及其类型、type/hierarchy/perspective 映射、逻辑层、文件名与目录、H1 和有序正文。身份按[命名规范](naming-conventions.md)解析后检查唯一性：APP 在当前治理联邦内唯一；MS 在所属 APP 内唯一；API 在所属 MS 内唯一；其余实体全局唯一。MS 的完整身份包含 APP，API 的完整身份包含 APP 和 MS；同一局部 ID 出现在不同合法宿主内不构成重复。

已读文件缺少必填宿主声明或同一完整身份重复落盘，判失败；宿主声明存在但目标不可读、存在歧义或所属库无法确定时，不猜全限定身份，标明待核实。全局唯一通过必须限定已覆盖的联邦范围，未读取范围保留待核实。

### 确定性关系

按所属视角 meta 检查必填关系，按[关系模型](entity-relations.md)检查动词、目标类型、正文位置、基数及反向要求。关系目标身份解析、引用解析与重复检测使用相同身份上下文。

- 既有 `1:1` 表示两端均至多一个对端；是否必须存在由必填规则另定。“多个”表示允许多个，不据此推导最少两个。
- 同库目标与反向关系可读时，缺少必填关系、非法边、基数超限或应有反向缺失判失败。检查全局入边上限时，必须覆盖完整相关范围。
- 联邦唯一 parent 表达归属，多方消费不增加 parent。消费方 `PD.uses_to SYS` 为单边事实，`SYS.used_by` 从消费声明派生，不要求手工回写；派生结果须说明消费库覆盖范围。
- 其他关系仍按真源的双向规则及明确例外检查；不得将单侧例外推广到全部关系。SYS 上游归属边与 `DS → MDG` 实现边的既有反向例外继续适用。
- 跨库目标不可读时，可先检查本侧必填、类型和引用形式；目标存在、反向一致性及完整基数列待核实，不把不可读当作目标不存在。

### 必需引用

按[引用规范](knowledge-reference-rules.md)检查关系、证据与导航中要求可达的本地引用，包括相对路径、bundle-relative 路径、引用式链接和章节锚点。目标不存在、锚点无效或越出允许范围判失败；代码示例、注释与合法纯 ID 不误作本地文件链接。

跨层 HTTP 按[联邦配置](federation-config.md)核对生成规则；默认离线不等于目标已核实。上级本地内容可读时核对目标，不可读时分别报告“形式检查结果”和“目标待核实”。纯 ID 也须执行适用的身份、类型与关系检查，不因没有链接而跳过。

## 结果与闭环

逐断言记录状态、对象、规则依据、证据与覆盖限制。下列英文名是统一入口的分项状态；汇总状态与 CLI 退出码见下文工具现状。

| 状态 | 语义 |
| --- | --- |
| 通过（PASS） | 所需上下文齐全，实际执行且满足断言；只对声明范围有效 |
| 失败（FAIL） | 已取得足够证据，确定违反适用规则 |
| 待核实（UNVERIFIED） | 断言适用，但来源不可读、身份歧义、快照变化或范围不完整，无法作结论 |
| 不适用（NOT_APPLICABLE） | 规则对该对象不适用，须说明理由或明确例外 |
| 未执行（NOT_RUN） | 应检查但尚未执行；不能当作通过或不适用 |

结构、确定性关系、必需引用和事实真实性分别报告。存在失败时不得报告整体通过；没有失败但仍有待核实或未执行时，只能报告已通过范围及未闭合项。警告文字不能代替上述状态，也不能把必需本地引用失败降为提示。

外库不可读时允许报告“本地通过、跨库待核实”，保留当前工作；依赖该外库核查的删除、迁移和注销不得闭环。后续取得来源后续验同一未闭合项，不以本地通过替代跨库完成。

事实真实性由已读来源及人工审查核实，沿用以上状态并记录依据。结构通过不证明事实真实；证据链接可达不证明内容支持结论；模板占位和示例数据不证明业务已经实现。

## 模板与兼容

模板/示例检查格式、关系规则及示例内部一致性，显式登记的占位不冒充生产事实；不得把占位豁免泛化为忽略非法类型、身份冲突或坏链接。业务实体须核实真实身份、宿主与来源，不以“示例数据”替代证据。模板检查通过与业务实体迁移通过分别报告。

`okf_version: 0.1` 继续表示基础交换格式，不表示本项目实体 Profile 已兼容。[项目 Profile v2](knowledge-profile-v2.md) 使用独立契约标识 `ai-knowledge/v2`，当前已部分接入校验工具，完整覆盖与发布仍待完成。采用基线按该契约记录于 `{DOC_DIR}/governance/profile.md`，包含规则所属版本、commit 及未提交内容哈希；不改根 OKF 版本，旧库不自动采用。兼容核验需记录旧/新规则基线、受影响实体与引用范围、迁移或保留策略，以及对当前业务快照的校验结果；缺少兼容证据时，不宣称升级或迁移完成。

## 工具现状与补核

**统一核心已接入，契约仍有未覆盖项。** [统一入口](../scripts/tools/validate-knowledge.sh) 与 `docs-build` / `docs-okf` 校验 CLI 共用结构、确定性关系与引用检查；两个技能保留导航/索引专属检查。只读默认全 DOC_DIR，支持局部选择，元库必须显式 `--layer` 与 `--bundle`。默认摘要，`--json` 输出五态证据、规则版本/commit/哈希、源快照与覆盖范围。FAIL 返回 1；无 FAIL 返回 0，但 UNVERIFIED/NOT_RUN 存在时汇总为 INCOMPLETE。不能仅凭退出码宣称完整合规。

校验不会替目标库自动采用当前 Profile 或证明旧规则兼容；采用仍保留待核实；事实未提供版本绑定的人工证据时保留未执行。可读上级库与 dependency 用于精确定位；当前库、显式消费库及其已登记 child 递归用于消费汇总，按实际文档根去重、防环。可读上级库用于目标与反向核验；未登记、不可读及未覆盖的下级/消费库不能据此判目标不存在。完整联邦唯一性与入边覆盖仍待核实。

| 已知工具边界 | 当前补核路径 |
| --- | --- |
| 统一 CLI 按稳定身份与实体树用途判型，错/缺 type 不降级；旧底层 Validator 类仍保留历史行为 | 对照 OKF Profile 先判型，再逐项核对；参考现有 docs-build 结构结果，不让类型错误降级 |
| 统一 CLI 从配置与显式参数取逻辑层，支持任意 DOC_DIR；旧底层接口不代表此结论 | 使用已解析逻辑层，人工核对实体 layer_scope、首次定义层和目录 |
| MS/API 按已读 implements_to 链解析完整身份；歧义/不可读宿主为 UNVERIFIED | 只对实际读取范围查重；缺少宿主证据不由目录补猜，不自动迁移 |
| 已检查允许边、必填、正文位置、本侧基数和已读目标反向；PD→SYS 已按只读登记派生；全域覆盖尚未完成 | 按本文件及关系真源人工补核，记录范围和未闭合依赖 |
| 统一入口必需本地链接和 Markdown 锚点违规为 FAIL；底层历史接口仍可能警告 | 使用现有本地链接工具补查，并核对其排除项与引用范围；未覆盖项人工核对 |
| 统一入口区分 HTTP 形式与目标读取，外库不可读标 UNVERIFIED | 单列外库可读性、形式检查、目标及关系核实状态 |
| 统一入口区分治理元数据与实体；来源证据已检查格式/身份/字节/指定提交，业务支持性仍依赖人工声明；旧底层类可能误判 | 保留原始非零退出及逐条诊断；确认文件为合法治理元数据后，按所属契约单项人工复核，不强套实体 Profile |
| 旧生成器与图工具未按新治理容器分型，可能误收证据或操作记录 | 生成前核对实际工具覆盖；不能保证治理元数据不进入实体图或台账时，停止受影响生成，保留原产物并报告未更新 |

现有命令及其实际能力见 [docs-build 工作流](../skills/docs-build/references/workflow.md)、[docs-okf 工作流](../skills/docs-okf/references/workflow.md)、[共享校验工具](../scripts/README.md#校验与测试)。补核结果按本文件汇总；未补核明确标为未执行，不虚构统一入口已上线。

仅已证明源于旧工具分型的治理元数据格式误报可以单项复核；记录文件、原诊断、适用规则与人工结果，不把脚本结果改报为成功。其他错误继续按真实断言核验，不批量豁免、降为警告或跳过。生成不兼容与只读校验误报分开处理：人工补核不授权旧生成器产出错误实体图。

## 证据与升级门禁

统一报告的 `context.evidence` 列已登记来源的版本检查、受影响目标和单独的历史恢复状态。当前实体匹配已核验记录且同目标当前证据无冲突时，`facts.attestation` 记录人工声明 PASS，明确工具未独立判断事实支持性；未提交文件可按当前字节核验，不冒称 Git 历史可恢复。详见[证据生命周期](knowledge-evidence.md#工具生命周期)。

[upgrade-compat.py](../scripts/tools/upgrade-compat.py) 将模板、业务、跨库、证据和旧基线分别报告，最终仅在 `can_advance_version: true` 时返回零。诊断模式的零退出只表示报告已生成。评估须绑定当前规则、所有已读输入及覆盖范围，并提供核验人、带时区时间和结论；旧基线为本库 governance 内的原始统一报告，规则字节须当前可读或能从指定完整 commit 核实。无法核实旧采用基线时保持 INCOMPLETE。

受影响实体依赖当前证据核验。未受影响实体只可沿用旧报告中同字节版本的事实 PASS；工具目前保守要求旧非规则输入均在本次读取且哈希一致，不能单凭目标未改继承旧结论。完整联邦覆盖的人工评估只批准所列范围，不授权范围外唯一性或迁移。工具不写 Profile 采用记录、DESIGN.version 或业务实体；最终步骤见[升级流程](../skills/docs-upgrade/references/workflow.md#兼容检查入口)。
