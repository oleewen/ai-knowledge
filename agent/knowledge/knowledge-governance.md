# 知识库治理规则

> **定位**：四层职责、实体首次定义层、层间基数与事实所有权冲突处理的唯一真源。字段必填性见五视角 meta；关系见 [entity-relations.md](entity-relations.md)；引用见 [knowledge-reference-rules.md](knowledge-reference-rules.md)；联邦配置见 [federation-config.md](federation-config.md)。组件入口见 [README.md](README.md)。

**最后更新**：2026-10-28

## 使命

使架构决策透明、一致、可追溯；同一事实只维护一处正文。

## 四层职责边界

| 层级 | 职责 |
| --- | --- |
| 公司 | 完整价值链、域架构、企业技术准入；不写单应用实现细节 |
| 解决方案 | 一个交付包的架构、主流程、产品框架、数据主权与技术选型；本层不首次定义 SYS，可由 PD 声明消费 |
| 系统 | 一个 SYS 的实现边界与架构聚合 |
| 应用 | 实现级实体、SDD 交付与物理锚点 |

跨层不得重复定义字段语义。阶段目录、槽位与流水线见 [知识布局](../references/knowledge-layout.md)，不在本文维护第二套路径表。

**联邦**：parent 仅允许 `application → system → solution → company`，向上 1:1；公司不直管系统。蒸馏按层上收，禁止默认跳层。

治理归属与业务消费分开：PD 可消费其他解决方案治理的 SYS，唯一 parent 不变；消费声明由 PD 维护，SLN 汇总，反向消费视图派生。消费不赋予写权限，不复制 SYS，也不替代 SYS 原有对标关系。关系语义见 [实体关系模型](entity-relations.md#共享系统消费)，定位见 [联邦配置](federation-config.md)。

**基数**：一仓一 SLN；一 SLN 一个 PL、一条 BP、多个 PD；BL→BSD-L1、BSD-L1→CAP、PL→BL、PD→BSD-L2、SYS→PD 均 1:1；一 SLN 多个 MDG、多个 TS。

`1:1` 约束两端各至多一个，是否必须存在由五视角 meta 的必填规则决定；可选关系不因此变成必填。“多个”表示允许多条，不统一要求至少两个；最低数量仍按必填规则确定。初始化模板的占位不计为已核实业务实体。

MS 必须且只能归属一个 APP，API 必须且只能归属一个 MS；APP 可含多个 MS，MS 可含多个 API。身份的唯一范围与解析见 [命名规范](naming-conventions.md#身份范围与限定引用)，不得从使用关系推导所有权。

## 各层聚焦摘要

**首次定义**指治理语义、字段口径和上游主定义所在层，不等于其他层不能提及。下游承接实现映射与物理锚点；上层实体不建下层 reference 文件，宿主目录可留。引用形态见 [引用规范](knowledge-reference-rules.md)。

| 首次定义层 | 实体 |
| --- | --- |
| 公司 | VC、BD、CAP、BSD-L1、BL、TPL |
| 解决方案 | SLN、PL、PD、BP、BSP、BSD-L2、BS、MDG、TS |
| 系统 | SYS、BSD-L3、BC、AGG、AB、PM、FT、FR、UC、BR、APP、MS、DS、ENT |
| 应用 | API、TBL、MW、CMP |

### 公司层

公司域架构说明 BD/BSD-L1 如何支撑 VC。产品视角只放企业产品标准，无产品实体；应用与数据视角无首次定义实体。各层目录见 [知识布局](../references/knowledge-layout.md)。

### 解决方案层

围绕交付包形成跨系统共性。SYS 的上游归属与对标由系统侧声明；解决方案不回写这两类边的反向关系。PD 的消费声明独立维护，不受该反向豁免限制；具体允许边见 [关系模型](entity-relations.md#例外与禁止)。

### 系统层

不复制上层实体。BSD-L2、MDG 仅作目录宿主；业务仓的聚合导航使用普通 README/index，不保留上层实体身份或 reference 副本。既有副本须核实导航引用后按迁移规则处理，不自动删除。需求分析从原始输入开始，不要求先有 SOLUTION。

### 应用层

承接上游实现映射。业务、产品视角无首次定义实体；本层需求分析同样可从原始输入开始。overview、章节归档与上行目标见 [overview 规范](overview-spec.md)和 [知识布局](../references/knowledge-layout.md)。

## 按事实所有权处理冲突

冲突按事实所有权处理，不以层级高低决定一方覆盖另一方。

| 对象 | 主定义与同步边界 |
| --- | --- |
| 已核实的实现现状 | 由相应下游事实源维护；上层摘要不得把实际未达标写成已达标 |
| 实体定义与字段口径 | 由首次定义层维护；下游实现差异不自动改写上游主定义 |
| 现行企业标准 | 由公司对应主定义维护；下游差异不自动修改或降低标准 |

发现偏离时，同时保留已核实现状与适用标准，显式记录差异及影响；按既有流程确认整改、限定范围的例外或标准修订。待决项保持待决，已有实现不等于例外获批。

有持久后果的技术或架构决定复用 [ADR 约定](adr-guidelines.md)，业务决定按原业务流程处理。业务 knowledge 正文只摘录已确认的决策要点，引用仍遵守 [引用规范](knowledge-reference-rules.md)，不直接链接 ADR。

## 实体事实与章节摘要

实体正文拥有 ID、属性和关系等结构化事实；视角章节负责解释、上下文与引用。章节内的编号、属性或关系表是实体的派生摘要，不形成第二份主定义。

涉及结构化事实变化时，先在首次定义层核实并更新实体，再同步受影响章节。纯解释且与现有实体一致时，无需重新构建实体。来源优先或目标优先的归档策略不能绕过这一边界；overview 候选不自动成为已确认事实。

实体更新与章节同步分别报告完成状态。未同步的摘要必须可定位、可追踪；全部受影响内容核验并获用户确认前，不将整项交接视为闭合。知识正文的引用仍遵守 [引用规范](knowledge-reference-rules.md)，流程记录不写入知识正文。

来源与派生实体/章节的持久关联遵 [知识证据契约](knowledge-evidence.md)。来源变化只触发待复核，不自动证明旧结论错误；会话记录与 TODO 不能替代证据登记。

## 身份迁移与删除

实体允许删除，历史正文仅通过 Git 查找，不要求另存退役实体或永久别名。API 换 MS、MS 换 APP 及实体 ID 变更均视为身份迁移；影响范围包含完整身份随之前缀变化的下属实体。

1. 列出旧/新完整身份及有效关系、章节摘要、导航和派生事实的影响范围。纯目录移动不代表迁移已完成。
2. 先完成有效依赖的迁移或解除；业务关系改变须有明确依据与授权，不能为消除断链自动删边。有效派生事实须迁移依据、独立复核或撤回，不能仅标待复核就算解除依赖。
3. 相关外库不可读、身份不明或检查范围不完整时，报告待核实，不关闭依赖该检查的删除或迁移；完成条件见 [统一校验](knowledge-validation.md)。
4. 获得针对具体对象的删除确认后，移除旧实体并复核引用。历史证据登记保留原身份与内容指纹，不属于有效业务引用；恢复能力按 [证据契约](knowledge-evidence.md) 单独核实。

未提交内容允许作为来源，但指纹不能恢复正文；没有匹配且可达的 Git 历史版本时不得承诺可恢复。不自动 commit、push 或创建源正文历史副本。
