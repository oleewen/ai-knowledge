# 应用架构

## 应用架构概述

本节阐明应用层的设计原则、风格选择与演进节奏，为服务拆分、集成与运维提供统一技术语境，并与业务架构、数据架构可对齐。

### 架构设计原则与约束

**应写内容**：非功能需求驱动的原则（可用性、性能、安全、可观测性、可演进性等）；组织与合规约束（技术栈、云平台、采购、数据出境等）；与业务架构一致的边界假设。原则需可检验，避免空泛口号。

**产出建议**：原则列表（每条附适用场景与反例）；约束清单及例外审批方式。

### 架构风格选型（单体 / 微服务 / SOA / 事件驱动等）

**应写内容**：当前及目标架构风格；选型理由、权衡与已知局限；与团队规模、发布频率、数据一致性强度的匹配说明。若混合风格，说明分域或分层的适用边界。

**产出建议**：一页决策摘要或 ADR 引用；可选对比表（维度 × 候选风格）。

### 架构演进路线图

**应写内容**：从中短期到长期的演进阶段、里程碑与触发条件；每阶段的主要风险与回滚策略；与项目/产品路线图的关系。标注「当前态 / 过渡态 / 目标态」。

**产出建议**：时间线或阶段表；关键里程碑与责任团队。

## 应用全景图

本节从系统外部到内部给出应用版图，支撑 impact 分析、新人 onboarding 与容量规划。

### 系统上下文图（C4-L1 Context）

**应写内容**：本系统与用户、外部系统、第三方服务之间的边界与主要交互；信任边界与数据出入方向。命名与业务术语表、集成清单一致。

**产出建议**：C4 L1 图（PlantUML、Mermaid 或配图）；图下列出主要外部依赖与协议类型。

### 应用 / 服务清单与职责

**应写内容**：每个应用或逻辑服务的名称、职责、负责人、生命周期状态（在建/运行/下线）；与业务能力或业务域的映射。避免职责重叠或「万能服务」无边界。

**产出建议**：服务清单表（可含仓库、语言、关键 SLA）；与业务架构「能力与系统映射」交叉引用。

### 应用分层结构（前台 / 中台 / 后台）

**应写内容**：分层模型（如渠道层、核心域服务、共享能力、支撑后台）及各层职责；跨层调用规则与禁止项（例如前台是否直连数据层）。若采用领域或产品线划分，说明与分层的正交关系。

**产出建议**：分层示意图 + 简短文字；可选「服务—分层」矩阵。

## 服务设计

本节将业务能力落地为可部署、可契约化的服务单元，并细化到容器与组件粒度，支撑实现与评审。

### 服务拆分策略与边界

**应写内容**：拆分维度（领域、子域、团队边界、数据自治等）；服务间耦合与内聚准则；与有界上下文、数据库归属的对应关系。说明何时合并或拆服务。

**产出建议**：拆分原则说明；可选「上下文映射」或服务边界列表。

### 各服务详细设计文档

**应写内容**：每一服务的职责边界；领域模型（聚合、实体、值对象及不变量）；对外接口契约（API/事件 schema、错误码、幂等与分页约定）；有状态流程时的状态机与并发策略。复杂服务可拆独立文档并在此索引。

**产出建议**：每服务一页摘要 + 链路至详细设计；模板字段至少覆盖职责、模型、契约、状态机四块。

### 服务容器图（C4-L2 Container）

**应写内容**：各容器（应用进程、数据库、消息中间件、网关等）及其技术选型；容器间协议与部署拓扑要点；与运行环境（K8s、VM 等）的关系。

**产出建议**：C4 L2 图；图下附容器清单表（名称、技术、端口/协议摘要）。

### 组件图（C4-L3 Component）

**应写内容**：关键服务内部的组件划分（应用层、领域层、基础设施层等）；组件职责与依赖方向；与代码仓库模块结构的对应关系。仅对核心或复杂服务强制 L3。

**产出建议**：选定服务的 C4 L3 图或包/模块依赖图；说明与 DDD 分层的映射。

## 服务间交互

本节描述同步与异步协作方式、编排与依赖治理，支撑故障定位、容量规划与解耦改造。

### 同步调用链路图

**应写内容**：主要用户场景下的同步调用链（入口、中间服务、下游）；超时、重试、熔断与降级策略摘要；与可观测性（Trace ID）的约定。

**产出建议**：序列图或调用链图；关键链路列表及 SLO/超时表。

### 异步消息 / 事件流图

**应写内容**：主题/队列/事件总线命名与分区策略；发布方、订阅方、载荷版本与顺序语义；与领域事件的对应关系。死信、重放与幂等要求说明。

**产出建议**：事件流或拓扑图；事件目录（名称、版本、Schema 位置）。

### 服务编排与协调（Saga / 工作流）

**应写内容**：长事务或跨服务流程的编排模式（编排器、协同、工作流引擎）；补偿与超时；与业务流程 L2/L3 的对应关系。说明与同步链路的选用边界。

**产出建议**：编排示意图或 BPMN 片段；关键 Saga/工作流清单及状态持久化方式。

### 服务依赖矩阵

**应写内容**：服务 A 对服务 B 的依赖类型（同步/异步/批）、方向与强度；循环依赖与热点依赖识别；依赖变更影响分析用法。

**产出建议**：矩阵表或图（行列为服务）；标注禁止的依赖模式。

## 接口管理

本节统一内外接口的发现、规范与演进，降低集成断裂与版本碎片化风险。

### 内部 API 目录与规范

**应写内容**：内部 REST/RPC/GraphQL 等 API 的目录结构、命名、认证与错误约定；OpenAPI/Proto 等契约存放位置与评审流程。与网关、服务网格策略一致。

**产出建议**：API 目录索引（可链路至各仓库）；内部 API 风格指南链接。

### 外部 / 开放 API 目录

**应写内容**：对合作伙伴或公众的 API 清单、用途与 SLA；与内部模型的差异（DTO、脱敏）；发布渠道（开发者门户、文档站点）。

**产出建议**：外部 API 清单表；与「集成架构」中的对外开放区分说明。

### 接口版本管理策略

**应写内容**：URL/Header/契约并存的版本策略；兼容窗口、弃用公告与下线流程；破坏性变更的审批与客户端影响评估。

**产出建议**：版本策略一页说明；与变更日志模板的对应关系。

### 接口变更日志

**应写内容**：按服务或 API 聚合的变更记录（新增、修改、修复、弃用）；关联版本号与发布日期；消费者需采取的行动。

**产出建议**：CHANGELOG 或等价机制；与 CI/发布流水线的挂钩说明。

## 集成架构

本节管理第三方与遗留系统集成，明确协议、数据流与防腐边界。

### 第三方系统集成清单

**应写内容**：系统名称、业务用途、对接团队、合同或 SLA 摘要、数据敏感度；与上下文图、服务清单一致。

**产出建议**：集成清单表；关键联系人及升级路径。

### 集成方式与协议

**应写内容**：HTTP、消息、文件、数据库直连等选型及适用场景；认证授权模式；批处理与实时边界。禁止或不推荐的模式（如跨库写）需写明。

**产出建议**：协议—场景对照表；安全与网络路径（VPN、专线、mTLS）摘要。

### 集成数据流图

**应写内容**：数据在系统间的流向、频率与批/实时属性；主数据与参考数据的权威源；与数据架构中同步任务的对应关系。

**产出建议**：数据流图或集成拓扑；关键接口与对象列表。

### 防腐层设计

**应写内容**：外部模型与内部领域模型的映射位置（ACL、Adapter）；转换规则、错误隔离与重试；何时引入防腐层 vs 直接 DTO。与术语映射表协同。

**产出建议**：关键集成的防腐层说明或类图；反模式警示（胖适配器、逻辑泄漏）。

## 多租户 / 多环境设计

本节说明租户隔离、环境拓扑与发布控制，支撑安全合规与交付节奏。

### 租户隔离策略

**应写内容**：模型（共享库共享表、共享库分表、分库、分集群等）；隔离维度（数据、配置、计算、网络）；与性能、成本、运维复杂度的权衡。合规与审计要求。

**产出建议**：租户模型说明图或表；跨租户操作的禁止项与审批。

### 多环境管理（开发 / 测试 / 预发 / 生产）

**应写内容**：环境用途、数据真实性、部署权限与发布路径；配置与密钥管理差异；环境间数据同步或脱敏策略。

**产出建议**：环境说明表；与 CI/CD、特性开关的衔接。

### 特性开关（Feature Toggle）

**应写内容**：开关类型（发布开关、实验、运维开关）、命名与生命周期；与配置中心或平台的集成；默认安全策略（如生产默认关）。

**产出建议**：开关管理规范；关键开关清单或登记方式。

## 关键设计决策记录（ADR）

本节沉淀重大技术决策的背景、选项与后果，便于审计、复盘与知识传承，并与实现保持可追溯。

### ADR 模板与编号规则

**应写内容**：ADR 标题格式、编号规则（如 ADR-YYYYMMDD-序号）、必填字段（上下文、决策、状态、后果）；存放路径与评审门禁。与项目 CONTRIBUTING 或设计规范一致。

**产出建议**：ADR 模板文件或片段；示例 ADR 链接。

### ADR 索引与状态维护

**应写内容**：全部 ADR 的索引表（编号、标题、状态：提议/通过/取代/废弃）；取代关系链；定期 review 责任。废弃 ADR 的归档方式。

**产出建议**：本文件内或独立 `adr/README` 中的索引表；状态变更流程。

### 待登记与占位说明

**应写内容**：尚未形成正式 ADR 但已口头约定的决策如何登记为「草案」或 issue；禁止长期用「xxx」占位而不补全。

**产出建议**：待决策 backlog 列表；与架构评审会议的节奏挂钩。
