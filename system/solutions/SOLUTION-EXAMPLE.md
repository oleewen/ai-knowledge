# 示例系统解决方案

> **结论**：在本系统内对齐「跨应用状态口径 + 运营异常定位入口」，不扩到公司级跨系统编排。  
> 读者：业务与产品。路径：`system/solutions/`。  
> 下游：[../analysis/ANALYSIS-EXAMPLE.md](../analysis/ANALYSIS-EXAMPLE.md)

---

## 1. 背景与目标

### 1.1 业务现状

本系统内多应用共担同一业务对象链路；运营在多应用间切换查状态，缺系统内统一的异常定位入口。

### 1.2 存在问题

应用间状态叫法不一 → 对内解释成本高；异常要跨应用拼证据 → 定位慢。

### 1.3 业务目标

| 目标编号 | 目标 | 度量 | 预期收益 |
| -------- | ---- | ---- | -------- |
| G-1 | 本系统内关键状态口径对齐并可追溯 | 高频状态无未解释歧义 | 少内部对账与扯皮 |
| G-2 | 运营可在系统内单入口定位卡点 | 典型异常定位耗时下降 | 快响应、少跨应用切换 |

---

## 2. 范围与约束

### 2.1 核心场景

运营按业务对象查询 → 看到本系统内各应用关键状态与时间点 → 明确卡点与下一步协作方。

### 2.2 涉及角色

| 用户角色 | 角色描述 | 核心关注点 |
| -------- | -------- | ---------- |
| 运营人员 | 异常与时效 | 定位快、证据齐 |
| 应用业务方 | 本应用环节处理 | 交接清晰、口径一致 |
| 客服/对内解释 | 对内说明状态 | 话术与系统一致 |

### 2.3 范围边界

#### 范围内（In Scope）

- 本系统内跨应用状态口径对齐与异常定位入口
- 与本系统 knowledge 五视角可落地的能力边界

#### 范围外（Out of Scope）

- 公司级跨系统编排与统一视图（见 `company/solutions/SOLUTION-EXAMPLE.md`）
- 改各应用原处理规则（本轮只对齐口径与定位呈现）

#### 成功标准

- 运营可在系统内单入口完成典型异常定位
- 高频状态解释口径一致（业务可验收）

---

## 3. 影响与冲突

### 3.1 影响面

- 运营：少跨应用切换
- 各应用业务方：状态命名/判定须对齐
- 对内解释：话术随口径收敛

### 3.2 影响业务能力

| 功能/业务能力 | 影响程度 | 影响类型 | 影响说明 |
| ------------ | -------- | -------- | -------- |
| 状态查询 | 高 | 口径调整 | 多应用拼盘 → 系统内统一入口 |
| 异常定位 | 高 | 追溯增强 | 关键时间点与责任环节提示 |
| 对内解释 | 中 | 承诺一致性 | 统一词典支撑话术 |

### 3.3 影响传播路径

```text
[状态查询] → [异常定位] → [应用协作] → [对内解释]
```

### 3.4 业务冲突

| 冲突编号 | 冲突描述 | 冲突类型 | 严重程度 | 化解方案 | 化解成本 |
| -------- | -------- | -------- | -------- | -------- | -------- |
| C-1 | 各应用对同一状态命名/判定不一致 | 规则/数据冲突 | 中 | 系统内统一词典 + 可追溯证据 | 中 |

---

## 4. 思路与方案

### 4.1 解决思路

**结论**：系统内先定状态词典与定位入口，再按高频链路扩展覆盖。跨系统统一视图不在本方案。取舍见 §5.2。

### 4.2 关键约束

| 约束类型 | 约束描述 | 影响 |
| -------- | -------- | ---- |
| 业务 | 系统内对外/对内解释须同一词典 | 冲突时以约定优先级 + 证据为准 |
| 资源 | 优先高频链路与高价值对象 | 不全量一次铺开 |
| 技术 | 正文不写实现栈；能力限制用业务话术 | 细节待研发确认 |
| 交付 | 无外部硬截止；每阶段可独立验收 | 节奏由优先级驱动 |
